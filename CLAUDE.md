# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm install
npm start            # unified: build if needed + server + open browser (-- --dev for hot reload)
npm run build        # vite build -> planner/portal/dist/ (required after any change to planner/portal/web/ or planner/logic/ before the server shows it)
node planner/portal/server/server.cjs   # serves planner/portal/dist/ + CSV API on 127.0.0.1:3000 (PORT env to change; PLANNER_DATA_DIR moves the data folder)
npm run dev          # Vite dev server with HMR; proxies /api to the backend, so run both
npm test             # node --test planner/test/*/*.test.mjs
node --test planner/test/logic/ids.test.mjs                  # single test file
node --test --test-name-pattern="renumber" planner/test/logic/ids.test.mjs   # single test by name
```

There is no linter or type checker. Tests cover only the pure modules (no DOM/React tests).

## Architecture

Local tools for a team lead's admin work (so far the backlog portal and its skills, and the `meeting-minutes` skill), split into four zones that depend on each other in one direction only (`app/` and `.claude/skills/` -> `planner/logic/`; nothing depends on `data/`'s contents):

- **`planner/logic/`**: pure logic, no DOM, no HTTP, shared by the frontend and the skill scripts. `csv.js` (parse/serialize), `story-text.js` (compose/parse the "As … I want… so that…" and acceptance-criteria cell text; the role keeps its article, so `asA` reads "a team lead" or "an approver", and `roleIsBlank` treats a bare "a" / "an" as empty), `file-name.cjs` (`validateName`, the one set of CSV file-name rules), `paths.cjs` (`DATA_DIR`, `GUIDELINES_DIR`; `PLANNER_DATA_DIR` env overrides the data folder, default `data/`), `backup.cjs` (backup folder name `YYYY-MM-DD_HHMMSS[-n]`, its validation, the three files of a backlog) and `flatten.js` (CSV -> one `Header: value` line per field, constant `----` between rows, used only to diff backups).
  - `model.js`: pure CSV <-> story model. Known columns (`COLUMNS`, including `Locked`: `Yes` or empty, valid only on a story with an ID) are matched by header name; unknown columns round-trip untouched in `story.cells`; unparseable User Story / User Acceptance Criteria cells keep raw text.
  - `ids.js`: story IDs (`IAM-0003`: epic-name initials + position within epic) are *derived*, not stable — `renumber` recomputes them on add/delete/reorder/move/open, and rewrites `Depends On` links (`;`-separated IDs) so they follow their story. Keep this invariant when touching story ordering. A **locked** story (`story.locked`) is a fixed point of `renumber`: it keeps its code, its epic keeps that code's prefix, and unlocked stories take the lowest free numbers around it (gaps are fine). The guards live here too: `moveStory`, `removeStory` and `commitEpic` leave a locked story alone, `applyBulk` skips the Epic of locked stories, `lockStories`/`unlockStories` skip stories without an ID, and `moveToProposed` refuses a locked story.
  - `review.js`, `proposals.js`, `proposal-input.js`: review-suggestion and proposed-story logic.
  - `lexicon.js`: the backlog's lexicon (`lexicons/<backlog file name>`, a CSV with `Term, Part of, Definition, Avoid, Notes`, `Avoid` `;`-separated; unknown columns round-trip in `cells`). `parseLexicon`/`composeLexicon`, and the term rules in one place for the Lexicon tab and the writer script: names unique ignoring case, a definition required, `Part of` must name a term (no self, no cycle), an `Avoid` word may not be a term name, a term with children cannot be deleted, a rename rewrites its children's `Part of`. Only problems a change introduces are refused, so an old problem in a hand-edited file never blocks an unrelated save. `applyTermItems` is the writer's add step (it refuses a term that exists).
- **`planner/portal/server/server.cjs`**: Node-built-ins-only server (no Express) serving `planner/portal/dist/` and a small CSV file API. `STORES` at its top is an allow-list mapping store name -> folder under `DATA_DIR` (`backlogs` for backlogs, `reviews` for review suggestions, `proposals` for proposed stories not yet in the backlog, `lexicons` for each backlog's defined terms, `lexicon-suggestions` for suggested term renames, deletes and edits). Only `.csv` files directly inside a registered folder are reachable. Backups are separate routes handled before the store lookup: `POST /api/backup/<file>` copies `backlogs/`, `reviews/`, `proposals/`, `lexicons/` and `lexicon-suggestions/` `<file>` (never the `.decided` sidecar) into `planner/data/backups/<file>/<date_time>/` (no overwrite, no partial folder on failure), `GET /api/backup/<file>` lists them, `GET /api/backup/<file>/diff?a=&b=` (a backup folder name or `current`) flattens both states and returns `git diff --no-index` output; git must be on the PATH for that route only. `backups` is deliberately not in `STORES`, so the file API cannot reach it.
- **`planner/portal/web/`**: multi-page Vite build (pages listed in `build.rollupOptions.input` in `planner/portal/web/vite.config.mjs`); `main.jsx` is the landing page. `shared/files.js` is the API client (`createFileStore(name)`: `list/read/create/write/rename/openFolder`), `shared/style.css` the common styles. `backlog-portal/` is the only tool so far: `graph.js` (dependency-graph layout for the Graph tab; `groupStories` folds the stories into features or epics for the Graph tab's Features and Epics levels, which are read-only and reuse `layoutGraph`), `hooks/usePanelSizes.js` (widths of the draggable list divider on the Editor, Proposed and Lexicon tabs, via `useListWidth.js`, and of the Stories table columns, kept in `localStorage` under `planner.listWidth.<tab>` / `planner.colWidth.<column>`; `ResizeHandle.jsx` is the drag handle, double-click resets; limits in `planner/portal/web/lib/panel-size.js`), `hooks/useCollapsed.js` (the Editor's folded epics and features, closed keys named by epic/feature name, kept in `localStorage` under `planner.collapsed.<backlog file>` and pruned once the backlog is loaded; the rules are in `planner/portal/web/lib/collapse.js`; `App` holds it, calls `reveal` when a story is added, accepted or given another Epic/Feature, and passes it to `StoryList` as the opt-in `collapse` prop, which also shows the Collapse/Expand epics and features buttons — the Proposed tab's list keeps its own unstored folds); with the opt-in `onLockGroup` prop each Epic and Feature head also has a lock button that locks or unlocks the stories of that group through `lockGroup` in `useBacklog` (`groupLockState` in `planner/logic/backlog/ids.js` gives the head's mark; nothing about the group is stored, so a story added later is unlocked), and the Proposed tab's list has none, `hooks/useBacklog.js` (reducer state) and `hooks/useAutosave.js` (debounced save, retries on failure e.g. file locked in Excel), `components/` the tabs (`BackupsTab.jsx` with `diff-lines.js` for git's colors; `LexiconTab.jsx` with `hooks/useLexicon.js`, which reuses `useAutosave` through its `serialize` option: an existing term saves when a field is left, a refused change stays on screen with the reason). The FileBar's Backup button first settles the backlog, proposals, review and lexicon saves (`settle` on each hook) so the backup matches the screen. It imports logic from `planner/logic/` by relative path.
- **`data/`** (git-ignored, private): `backlogs/`, `reviews/`, `proposals/`, `lexicons/`, `lexicon-suggestions/`, `backups/`, `meetings/` and `logs/` (the last three are not stores; `logs/writes.jsonl` is the write log). Store names in code, skills and specs (`backlogs/`, `reviews/`, `proposals/`, `lexicons/`, `lexicon-suggestions/`) are relative to this folder.
- **`ai/`**: `guidelines/` (`product-backlog.md`, `sprint-points-guideline.md`), `launchers/` (the `.ps1` session starters) and `mcp/` (the `backlog-tools` MCP server for the story sessions; it imports the skill scripts' exported functions and `planner/logic/`). `.claude/skills/` and `openspec/` stay at the repo root because Claude Code and the OpenSpec CLI look for them there.

**`toolkit/`** is a fifth, standalone zone: reusable Claude Code skills (`skills/`), slash commands (`commands/`: `jois`, `opsx`), rules (`rules/`) and a PowerShell installer (`install/Install-Toolkit.ps1`) that copies them into `~/.claude` or a project. It depends on nothing above and nothing depends on it; it has its own tests (`cd toolkit; python check_toolkit.py; python -m pytest`, needs Python and pytest), separate from `npm test`. Its own `openspec/` documents it. Install and usage instructions are in `toolkit/README.md`; read that rather than restating it here.

Adding a new tool: see the "Add a new tool" steps in `README.md` (new `planner/portal/web/<tool>/` dir, add to vite inputs, register data folder in `STORES`, link from `planner/portal/web/main.jsx`).

## Workflow

Changes are managed with OpenSpec (`openspec/`): `specs/` holds the current capability specs (`csv-file-store`, `user-story-editor`), `changes/` holds proposals/archives. Use the `opsx:*` skills (propose / apply / archive). Commits use conventional-commit prefixes (`feat:`, `style:`, `chore(openspec):`).

The `review-backlog` skill (`.claude/skills/review-backlog/SKILL.md`) reviews a backlog CSV against `planner/guidelines/product-backlog.md` (hierarchy, INVEST, acceptance criteria and its edge-case checklist, section 7) and across stories, the backlog's lexicon and its proposals, and reports; it never edits the backlog CSV. `read-backlog.mjs <backlog> [section]` serves the context in sections so a large backlog is never read in one output: no section prints the scope line and a menu with sizes; `guidelines`, `sizing` (`sprint-points-guideline.md`), `lexicon`, `proposals` (benched stories left out and counted), `checks` and `epic-<n>` (the header row and that Epic's stories) print one each, and `guard-bash.mjs` allows a section of the form `[a-z]+(-\d+)?` after the file name. `checks` is `backlogChecks` in `.claude/skills/review-backlog/backlog-checks.js`, which reuses `backlogProblems`, `storyIssues` and `lexiconProblems` and adds duplicate Epic/Feature/Title, overlap with a non-benched proposal, an `Avoid` word used (whole word) in a story, off-scale points and a Clarifications pair that is answered but not resolved. The skill reads every Epic in turn, writes its findings in batches per Epic, and reports a Consistency heading for what only shows across stories. `Consistency` is a fifth Area in `AREAS`; a dependency problem stays `INVEST`. Every dependency problem (a link that does not exist, names the story itself or a still-proposed story, or a cycle) gets a `remove` row on `Depends On`: a `remove` deletes the entry the story lists, whether or not a story holds it, and `targetTitle` is needed only when a story holds the code (an `add` keeps all its checks). The skill may write `resolve` rows (`pair` names the question) and never writes the lexicon or the proposals. Its suggestions are written to `planner/data/reviews/<backlog>.csv` only through `.claude/skills/review-backlog/write-review.mjs` (validation and CSV logic in `planner/logic/review/review.js`, shared with the portal's Apply/Dismiss). A long review is written in batches: the first run replaces the review, later runs add `--append` (each batch validated alone; `guard-bash.mjs` allows both forms). Statuses the user already decided are kept aside in `planner/data/reviews/<backlog>.csv.decided` so later batches can restore them. Locked stories are reference only: `read-backlog.mjs` prints the scope line `N of M stories submitted for review, K locked (reference only)` in the menu and in `checks`, the skill does not review locked stories, and for a strong objection writes an `unlock` row (empty Field/Suggested). The writer requires an `unlock` row in the resulting review file (an earlier batch counts) for every field-edit row on a locked story, and the portal shows such suggestions with Apply disabled until the story is unlocked. A criterion `replace` or `remove` row finds its criterion by the text in `Current` (`locateCriterion` in `planner/logic/review/review.js`; the `AC<n>` label is only a hint, tried first), so rows of one story can be applied in any order even though a removal renumbers the criteria after it.

The `explore-stories` and `propose-stories` skills draft new stories and edits to existing ones, and reach the data only through the **`backlog-tools` MCP server**, `planner/claude/mcp/backlog-tools.mjs` (stdio, `@modelcontextprotocol/sdk`; no Bash, `Read` or `Grep` in these sessions). Its eight tools call the same exported functions as the scripts (`suggest_lexicon_change`, `search_stories` and `read_file` have no script form), so validation and error text are the scripts': `search_stories` (`backlog` and `query` only: the stories of the backlog and of its proposals, benched ones left out, in which every word of the query appears in some field, the rule of the Stories tab search via `matchesQuery`; one `ID | Title | Epic > Feature | backlog or proposed` line each, at most 25 and then how many more matched; no match is a normal reply, a blank query an error pointing to the `index` section; the skills use it instead of reading the `index` to find related stories, then read one story with `read_context` `storyId` + `storyTitle`; `searchStories` in `read-story-context.mjs`, `findStories` and `searchReply` in `planner/logic/backlog/story-search.js`), `read_context` (`backlog` optional, then at most one of `section` or `storyId` with `storyTitle`; `storyIds`, a list of `{id, title}`, only with section `reviews`), `check_drafts` (the writers' validation for `items`, `terms` and `rows`, each alone, against the files as they are now; it writes nothing and tells the stories a writer would skip as repeats), `write_proposals`, `write_lexicon`, `suggest_lexicon_change` and `write_review` (always appends); `read_file` (`backlog`, `file` `lexicon` or `proposals`, then one of `pattern`, a case-insensitive plain-text match, not a regular expression, that returns the header row and up to 50 matching lines with their line numbers, or `offset` and `limit`, which return those lines, 100 by default and at most 200; neither returns only the size and the line count; `readFile` in `read-story-context.mjs`) reads the backlog's lexicon or proposals in parts and chooses the file from the backlog name and `file` alone, so no path is accepted and nothing else is reachable. `node planner/claude/mcp/backlog-tools.mjs --read-only` exposes `read_context`, `search_stories` and `read_file` only. Each tool's description carries its rules (the review-row rules included: one `AC<n>: Given…, when…, then…` line per row, a `replace` starts with the label of the criterion it replaces, a `remove` takes the label alone, an `unlock` row for a locked story), built from the exports of `planner/logic/review/review.js`; `test/backlog-tools-mcp.test.mjs` checks them. **Stories are named by Title**: backlog IDs shift on every `renumber`, so the tools require an existing story's current Title next to its ID (`storyTitle` on `read_context`, review rows and patches; `{id, title}` in `dependsOn` and `storyIds`; `targetTitle` on a `Depends On` review row; `NEW-<k>` references inside one call stay bare). `resolveStoryRef` in `planner/logic/backlog/story-ref.js` compares the pair (trimmed, case-folded); on a mismatch nothing is written and the reply says what the ID holds now and lists the stories with that Title (ID, Epic > Feature), so the agent reads the right one and repeats the call, or asks the user when it cannot tell. The Titles are only a check: they are not stored, and the CSV files, the review file and the portal stay ID-based. The skills call stories by Title in everything the user reads. The scripts (`read-story-context.mjs`, `write-proposal.mjs`, `write-lexicon.mjs`, `review-backlog/write-review.mjs`) remain thin CLI wrappers over the same functions; they take bare IDs as before and check a Title only when one is given (the tools pass `requireTitles`). The launchers write a `--mcp-config` file into the temp folder (`planner/claude/launchers/backlog-tools-config.ps1`) and start Claude with `--tools "Skill,AskUserQuestion" --strict-mcp-config --allowedTools mcp__backlog-tools__read_context mcp__backlog-tools__search_stories mcp__backlog-tools__read_file mcp__backlog-tools__check_drafts --permission-mode default` (`explore-stories.ps1` runs the `--read-only` server and pre-approves `read_context`, `search_stories` and `read_file`): the tools that write nothing are pre-approved, the writers are not, so Claude Code asks before each write. The skills' `allowed-tools` list `read_context`, `search_stories` and `read_file` (and, for `propose-stories`, `/story:propose` and `/story:review`, `check_drafts`) only, for the same reason; `--permission-mode default` keeps the prompts on even if your own settings use auto mode.

`explore-stories` only discusses (never writes); it asks the shape-deciding question first and checks a new or renamed term against the terms and `Avoid` lists, listing the definitions and stories it touches, before drafting. `propose-stories` runs `check_drafts` on the drafts first and fixes what it reports, shows the complete final text of every draft in one reply (numbered in write order, never "as before"), asks one yes/no, and after a separate confirmation reprints the drafts right before each writer call; a text too long for one reply is split by writer with a yes/no for each. `write_proposals` takes a list of **new stories** (no `id`) and **patches** (an `"id"` of a proposed story, `NEW-<n>`, plus only the fields to change; validation in `.claude/skills/propose-stories/proposal-input.js`). New stories are added to `planner/data/proposals/<backlog>.csv` with `NEW-<n>` IDs by the portal's rule (`nextPlaceholder`); a patch changes the named fields of that story in place (keeping its position, Benched and unknown columns), is validated as the merged story, may carry `clarifications` (a new story: a list of questions; a patch: `{add:[questions], answer:[{n,text}], resolve:[{n,note}]}`, where an answer is accepted only on an existing pair whose answer is empty, `resolve` appends the note (the decision, composed by the skill) to Notes on a new line and removes pair `n` whether or not it has an answer, and otherwise pairs are never deleted or overwritten; Notes may have several lines, every other text field one), and is refused for a benched story or one whose stored User Story/Criteria is free text it does not replace. One invalid item writes nothing. It creates the file with the backlog's columns when missing, never removes a proposal and never writes `planner/data/backlogs/`. `propose-stories` (and `/story:propose`, the same without the yes/no) also writes agreed changes to stories already in the backlog as review rows through `write_review`: never `add-story` rows or groups (new stories go to the proposals), the existing Area values, and an `unlock` row with the edits of a locked story. It runs the lexicon writer, then the proposal writer, then the review writer; a rejected later call is fixed and resent alone, and an earlier one is not rerun once its read-back matched. After **every** writer call it reads that file back in the same turn (`read_context` for reviews and lexicon suggestions, `read_file` for the proposals and the lexicon) and calls something written only when the read-back matches (never on the writer's reply alone, and never on its own earlier "done"); on a mismatch it says what is missing and sends only that part. A new story whose Epic, Feature and Title (trimmed, case-folded) are already in the proposals is skipped and reported with the ID it matched, so a repeated `write_proposals` call is safe; each writer re-reads its file after the atomic write and fails, naming what is missing, if the file does not hold it (`checkProposal`, `checkLexicon` and `checkReview` are the writers' validation without the write). `planner/logic/storage/write-log.cjs` appends one JSON line (time, writer, store, file, bytes, short hash; no contents) to `planner/data/logs/writes.jsonl` for every save by the portal's file API and by the writers, so the last writer of a file can be found; `logs` is not a store. `propose-stories` re-reads the context at the start of every use (a patch builds on the file as it is now), shows old and new values for each patch before its yes/no, and prefers a patch to a second story. `read_context` returns one section per call (so a result stays small enough to be shown in full): `guidelines` is `product-backlog.md` then `sprint-points-guideline.md` for sizing, `index` the backlog as an index (`ID, Epic, Feature, Title, User Story, Sprint points, Depends On, Locked`); `reviews` the review file's row count and open rows per story (with `storyIds`, the open rows of those stories in full) and `lexicon-suggestions` the open term suggestions, which exist to verify the other writers; with only a backlog it returns a menu of the sections with their sizes and, after them, the proposals and lexicon files (size, and for the proposals the number of benched rows, or "does not exist yet"; both are read with `read_file`). **The lexicon and the proposals are not sections** (they can be large, a 50KB lexicon did not fit one result): `read_context` answers a request for either with an error that names `read_file`, and the session reads them with that tool, with no hook and no confirmation step: the sessions have no `Read` or `Grep`, because the project's `.claude/settings.json` denies `Read(./data/**)` and a deny wins over any allow rule or hook (`--setting-sources user` would drop the project's skills too). Benched proposals are no longer filtered out of what the skills see: they ignore rows with `Benched: Yes`, and `write_proposals` still refuses to patch one. `explore-stories.ps1` asks for the backlog itself when none is given. With a backlog-tools result, `read_context` still returns data labelled as such; the skills treat the output of `read_file` as data too, with a `storyId` one backlog story with every column (the skills read a backlog story that way before showing, patching or editing it), and with nothing it lists the backlogs. The sessions are started by `planner/claude/launchers/explore-stories.ps1` (`--read-only`) and `planner/claude/launchers/shape-stories.ps1 [backlog] [story]` (backlog with or without `.csv`; story is one argument, a `NEW-<n>` of that backlog, a story ID of the backlog such as `IAM-0004`, or quoted free text; the script prompts for what is missing, rejects an unknown backlog, an empty story, a `NEW-<n>` not in that backlog's proposals or a backlog ID not in `backlogs/`, then starts in `/explore-stories` with both filled in (a `NEW-<n>` or backlog ID goes in as `NEW-57 titled "Reset password"`, the Title read from the file; free text as typed) and all eight tools, so `/propose-stories` can follow in the same session). Two read-only commands help in that session: `/story:re-read` (after you changed the backlog, proposals or lexicon yourself: re-reads the sections, the proposals and lexicon files and the stories under discussion by Title, reports what changed, drops stale drafts) and `/story:review` (an audit of only what is under discussion — the stories shaped, their dependencies, the terms they use and what was written — ending in a checklist split into yours in the portal, `/story:propose` and decisions; `review-backlog` stays the whole-backlog check). Every story has a `Clarifications` column (`Q1: …` / `A1: …` pairs, an empty answer = open; edited in the story form, "N open" badge in the lists; open questions block nothing; `planner/logic/backlog/story-text.js` parses and composes it). The rule for drawing questions out is written once in `product-backlog.md` section 6 and cited by both skills; `review-backlog` suggests questions as `Clarifications` `append` rows (Area `Clarification`), which Apply adds as open questions. `propose-stories` also writes a `Clarifications` `resolve` row when the user answers a question of a backlog story: the finding names the question by `pair` (its number in the story read), the writer stores the question text in `Current` (`locatePair` finds it by that text, so rows apply in any order), `Suggested` is the decision, and Apply adds it to Notes on a new line and removes the question in one edit (`resolvePair` in `planner/logic/review/review.js`, shared by Apply and Accept all). No skill writes `backlogs/`: a backlog story gets questions from the portal, from a review suggestion (including one written by `propose-stories`), or after moving it to Proposed. A proposed story can be **benched** (`Benched`: `Yes` or empty, a column only proposals files have; a checkbox in the Proposed tab's form): a benched story cannot be accepted (Accept and Accept all are disabled until it is un-benched), and the two skills ignore benched stories by instruction (the proposals file is read as it is, so benched rows are visible to them). The skills' `locked-settings.json` files set `claudeMdExcludes` (`**/CLAUDE.md`, `**/.claude/rules/**`), so launcher sessions do not load this file or the user-level rules. Each backlog also has a **lexicon**, `planner/data/lexicons/<backlog>.csv` (the portal's Lexicon tab, backed up with the backlog): defined terms, each with an `Avoid` list of words stories must not use and an optional `Part of` parent ("Dataset attribute" under "Dataset"). The sessions read it with `read_file` (a term or an `Avoid` word is looked up with its `pattern`), and both skills use the terms by full name and never an avoided word. `propose-stories` (and `/story:propose`) also adds new terms through `write_lexicon` (a list of `{term, definition, avoid?, notes?, partOf?}`; same rules as the tab; written straight into the file, no staging; a term that already exists is rejected, and it never changes, removes or renames one), shows them in the same reply and the same single yes/no, and runs it before the proposal writer so a story can use a term defined in the same run. An edit (definition, avoid, notes, part of), rename or delete of an existing term goes through `suggest_lexicon_change` (`{term, action: rename|delete|edit, newName?, avoid?, avoidOldName?, definition?, notes?, partOf?, reason}`; an edit replaces each field it names, `avoid` as a whole list; validation, parsing and the impact in `planner/logic/lexicon/lexicon-suggestions.js`, the file side in `propose-stories/suggest-lexicon.mjs`): it appends open rows to `planner/data/lexicon-suggestions/<backlog>.csv` (`Term, Action, New name, Add to Avoid, Reason, Status, Edit`; `Edit` is JSON `{field: {from, to}}` for an edit row, and the row is stale once the term differs from `from`) and returns the impact (children, definitions that use the name, Avoid clashes) without touching the lexicon. The Lexicon tab (`useLexiconSuggestions.js`) lists open ones; Apply runs `applySuggestion` through the lexicon reducer (a rename and its checked Avoid words are one `saveTerm`, so the old name can be avoided at once; a delete is refused while the term has children; an edit saves the `to` values, shown in the tab as a word diff per field, and Apply or Dismiss covers the whole suggestion) and sets `applied` only when accepted. It runs after `write_lexicon` and before the proposal writer. Like the review skill, both cite `planner/guidelines/product-backlog.md` and do not restate it.

The `meeting-minutes` skill (`.claude/skills/meeting-minutes/`) turns notes pasted into the session into minutes following `template.md` in its folder. It asks the user for every field the notes lack (a skipped one shows `[TBC]`), attributes a point to a person only when the notes do, shows the minutes, and after confirmation saves them through `write-minutes.mjs "<title>" <YYYY-MM-DD>` (minutes on stdin) to `planner/data/meetings/<slug>_<YYYY-MM-DD>.md`. The writer never overwrites: a taken name gets `_1`, `_2`, ...; `write-minutes.mjs --replace <file name>` swaps the content of an existing file and is used only when the user says the notes refine saved minutes. `meetings` is deliberately not in `STORES` (the file API and the portal cannot reach it). `planner/claude/launchers/meeting-minutes.ps1 ["notes"]` starts a locked session (Bash, Skill and AskUserQuestion only; asks for the notes, ended by `END` on its own line, when not given): its `locked-settings.json` runs `.claude/skills/meeting-minutes/guard-bash.mjs`, which allows only the two writer forms with a `<<'MINUTES'` heredoc and nothing else, and sets `claudeMdExcludes` like the story launchers.

The repo is ESM (`"type": "module"` in `package.json`); `planner/portal/server/server.cjs`, `planner/logic/storage/file-name.cjs` and `planner/logic/storage/paths.cjs` stay CommonJS (the `.cjs` extension), so the server and the ESM skill scripts can share them.

`planner/guidelines/product-backlog.md` is the single source of backlog standards (epic/feature/story/AC definitions, the 13-point size cap, INVEST) used for both writing and reviewing stories; the review skill cites it and does not restate it. `planner/guidelines/sprint-points-guideline.md` covers point sizing benchmarks.
