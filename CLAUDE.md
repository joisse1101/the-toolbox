# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run the `npm` commands from `planner/`, which holds `package.json`, `package-lock.json` and `node_modules/` (the toolkit has none; the `jois-story-plan` skill has its own `package.json` for the Mermaid check).

```
cd planner
npm install
npm start            # unified: build if needed + server + open browser (-- --dev for hot reload)
npm run build        # vite build -> planner/portal/dist/ (required after any change to planner/portal/web/ or planner/logic/ before the server shows it)
node planner/portal/server/server.cjs   # serves planner/portal/dist/ + CSV API on 127.0.0.1:3000 (PORT env to change; the data folder comes from `planner/planner.config.yaml`, or the file `PLANNER_CONFIG` names)
npm run dev          # Vite dev server with HMR; proxies /api to the backend, so run both
npm test             # node --test --import ./test/setup.mjs test/*.test.mjs test/*/*.test.mjs (setup.mjs points PLANNER_CONFIG at test/sample-config.yaml, whose dataDir is test/sample-data/)
node --test planner/test/logic/ids.test.mjs                  # single test file
node --test --test-name-pattern="renumber" planner/test/logic/ids.test.mjs   # single test by name
```

There is no linter or type checker. Tests cover only the pure modules (no DOM/React tests). `npm test` never reads the real `planner/data/`: `planner/test/setup.mjs` (loaded with `--import`) sets `PLANNER_CONFIG` to the committed `planner/test/sample-config.yaml`, whose `dataDir` is the committed `planner/test/sample-data/` (same layout as `planner/data/`; read-only, a test that writes uses a temp copy) and a guard test in `paths.test.mjs` fails if it is dropped. A test run alone with plain `node --test <file>` skips the setup file, so a test that needs data sets `PLANNER_CONFIG` itself (a test that saves the config points it at a temp copy).

## Architecture

Local tools for a team lead's admin work: the backlog portal in `planner/`, and the story skills that live in `toolkit/`. **`planner/`** is the backlog planner: the portal shows and edits backlog files, and the story skills (global toolkit items) write suggestions, proposals and lexicon terms into the same files in `planner/data/`. The two meet only in those files. **`toolkit/`** is separate and global (below). The zones depend in one direction only, enforced by `planner/test/zones.test.mjs`: `planner/logic/` imports nothing outside itself; `planner/portal/` imports `planner/logic/` and `planner/guidelines/`; `toolkit/` imports nothing outside itself. Nothing in `logic/` imports the portal, and nothing imports `planner/data/`'s contents:

- **`planner/logic/`**: pure logic, no DOM, no HTTP, shared by the portal and, as a generated copy, by the story skills, in folders by domain. `backlog/csv.js` (parse/serialize), `backlog/story-text.js` (compose/parse the "As … I want… so that…" and acceptance-criteria cell text; the role keeps its article, so `asA` reads "a team lead" or "an approver", and `roleIsBlank` treats a bare "a" / "an" as empty), `storage/file-name.cjs` (`validateBacklogName`, the one set of backlog-name rules: a trailing `.csv` is dropped, separators, invalid Windows characters and the reserved name `logs` are refused), `storage/backlog-paths.cjs` (the one place that builds the path of a backlog's file from its name and a kind: `backlogDir`, `backlogFile`, `reviewDecidedFile`, `slicesDir`, `contextMapFiles`, `logFile`, plus `listBacklogs` and `detectOlderLayout`; the layout is in the `planner/data/` note below), `storage/paths.cjs` (`DATA_DIR`, the folder named by `dataDir` in the project config as read at load, for short-lived scripts; `getDataDir()`/`setDataDir()` are what the server and the write log use so a switch takes effect at once; `legacyDataHint` says how to move data an earlier layout left in `data/` or `user-stories/`), `storage/project-config.cjs` (reads, validates and saves `planner/planner.config.yaml`, or the file `PLANNER_CONFIG` names: `projectName` and `dataDir`, a bad key fails naming it), `storage/project-folders.cjs` (the folder checks, `initFolders`, `copyData` and `migrateOlderLayout` the Settings tab uses: init creates only the data folder and `logs/`, copy skips any `backups/` folder, and the migration copies the older layout per backlog on request, never changes or overwrites a file, reads each copy back and reports the files it could not match) and `storage/write-log.cjs` (logs backlog and kind). `skill-support/` holds the helpers only the skills use (`write-atomic.mjs`, `paths.cjs` with `GUIDELINES_DIR`, `resolve-data-dir.mjs`, below), and portal-only code with the portal (`planner/portal/web/lib/`: `collapse`, `panel-size`, `story-table`, `word-diff`). There is no backup feature.
  - `backlog/model.js`: pure CSV <-> story model. Known columns (`COLUMNS`, including `Locked`: `Yes` or empty, valid only on a story with an ID) are matched by header name; unknown columns round-trip untouched in `story.cells`; unparseable User Story / User Acceptance Criteria cells keep raw text.
  - `backlog/ids.js`: story IDs (`IAM-0003`: epic-name initials + position within epic) are *derived*, not stable — `renumber` recomputes them on add/delete/reorder/move/open, and rewrites `Depends On` links (`;`-separated IDs) so they follow their story. Keep this invariant when touching story ordering. A **locked** story (`story.locked`) is a fixed point of `renumber`: it keeps its code, its epic keeps that code's prefix, and unlocked stories take the lowest free numbers around it (gaps are fine). The guards live here too: `moveStory`, `removeStory` and `commitEpic` leave a locked story alone, `applyBulk` skips the Epic of locked stories, `lockStories`/`unlockStories` skip stories without an ID, and `moveToProposed` refuses a locked story.
  - `review/review.js`, `backlog/proposals.js`: review-suggestion and proposed-story logic (`proposal-input.js` is the proposal writer's and `backlog-checks.js` the review skill's; both live in their skill folders in `toolkit/skills/`).
  - `lexicon/lexicon.js`: the backlog's lexicon (`<backlog>/lexicon.csv`, a CSV with `Term, Part of, Definition, Avoid, Notes`, `Avoid` `;`-separated; unknown columns round-trip in `cells`). `parseLexicon`/`composeLexicon`, and the term rules in one place for the Lexicon tab and the writer script: names unique ignoring case, a definition required, `Part of` must name a term (no self, no cycle), an `Avoid` word may not be a term name, a term with children cannot be deleted, a rename rewrites its children's `Part of`. Only problems a change introduces are refused, so an old problem in a hand-edited file never blocks an unrelated save. `applyTermItems` is the writer's add step (it refuses a term that exists).
- **`planner/portal/server/server.cjs`**: Node-built-ins-only server (no Express) serving `planner/portal/dist/` and a small CSV file API. `STORES` at its top is an allow-list of the five kinds from `backlog-paths.cjs` (`backlog`, `review` for review suggestions, `proposals` for proposed stories not yet in the backlog, `lexicon` for the backlog's defined terms, `lexicon-suggestions` for suggested term renames, deletes and edits); the API is `/api/<kind>/<backlog name>`, the name carries no `.csv`, and the server resolves it to the kind's fixed file in the backlog's folder under the current data folder. `list` returns the backlog folders, create makes the folder with an empty `user-stories.csv` (numbered on a name conflict) and rename renames the folder. Slices, `logs` and everything else are not kinds, so the file API cannot reach them. The settings routes are handled before the store lookup: `GET /api/project` (name, served data folder, config path), `PUT /api/project` (`{projectName?, dataDir?}`: saves the config through `saveConfig`, and for a `dataDir` switches the served folder at once, refused with `busy` (409) while a write, create, rename, init, copy or migration is running, and with `refused` (400) when `confineDir` or `saveConfig` refuses), `POST /api/project/check` (`{dir}`: `refused`, `has-planner-files` (a backlog folder), `older-layout` (no backlog folder but a folder of the older layout), `empty` or `missing`), `POST /api/project/init` and `POST /api/project/copy` (`{dir}`: confined first, copy goes from the served folder, never overwrites), `POST /api/project/migrate` (no body, needs the same-origin header: runs `migrateOlderLayout` on the served folder, answers the copied and skipped lists; never runs unasked). `POST /api/project/pick` (no body: opens the system folder dialog and answers `{dir}` or `{cancelled: true}`, or 500 `picker-unavailable` when the dialog cannot open; it saves and switches nothing, and tests replace the dialog through `setFolderDialog`). Like every route they answer only a loopback Host, and a bad config ends the server at startup naming the key.
- **`planner/portal/web/`**: multi-page Vite build (pages listed in `build.rollupOptions.input` in `planner/portal/web/vite.config.mjs`); `main.jsx` is the landing page. `shared/files.js` is the API client (`createFileStore(kind)`: `list/read/create/write/rename/openFolder`, the backlog named without `.csv`), `shared/style.css` the common styles. `backlog-portal/` is the only tool so far: `graph.js` (dependency-graph layout for the Graph tab; `groupStories` folds the stories into features or epics for the Graph tab's Features and Epics levels, which are read-only and reuse `layoutGraph`), `hooks/usePanelSizes.js` (widths of the draggable list divider on the Editor, Proposed and Lexicon tabs, via `useListWidth.js`, and of the Stories table columns, kept in `localStorage` under `planner.listWidth.<tab>` / `planner.colWidth.<column>`; `ResizeHandle.jsx` is the drag handle, double-click resets; limits in `planner/portal/web/lib/panel-size.js`), `hooks/useCollapsed.js` (the Editor's folded epics and features, closed keys named by epic/feature name, kept in `localStorage` under `planner.collapsed.<backlog>` and pruned once the backlog is loaded; the rules are in `planner/portal/web/lib/collapse.js`; `App` holds it, calls `reveal` when a story is added, accepted or given another Epic/Feature, and passes it to `StoryList` as the opt-in `collapse` prop, which also shows the Collapse/Expand epics and features buttons — the Proposed tab's list keeps its own unstored folds); with the opt-in `onLockGroup` prop each Epic and Feature head also has a lock button that locks or unlocks the stories of that group through `lockGroup` in `useBacklog` (`groupLockState` in `planner/logic/backlog/ids.js` gives the head's mark; nothing about the group is stored, so a story added later is unlocked), and the Proposed tab's list has none, `hooks/useBacklog.js` (reducer state) and `hooks/useAutosave.js` (debounced save, retries on failure e.g. file locked in Excel), `components/` the tabs (`SettingsTab.jsx` with `hooks/useSettings.js` (project name and data folder: the data folder box is read-only, and Change folder opens the system folder dialog through `POST /api/project/pick`, opened by the server because a browser cannot return a full path; the chosen folder goes through check, offer and a live switch through the server's settings routes, an offer to create the data folder or copy the data into a new folder, and a Migrate action when the folder holds the older layout; skill sessions use the new folder once restarted), `LexiconTab.jsx` with `hooks/useLexicon.js`, which reuses `useAutosave` through its `serialize` option: an existing term saves when a field is left, a refused change stays on screen with the reason). The FileBar shows a notice when the data folder holds the older layout. It imports logic from `planner/logic/` by relative path.
- **`planner/data/`** (the default data folder, git-ignored, private; the project config's `dataDir` can name another, and the notes below apply to whichever folder is served): one folder per backlog, `<backlog>/` (a folder is a backlog when it holds `user-stories.csv`), and `logs/` (`logs/writes.jsonl` is the write log; `logs` is reserved and cannot be a backlog name). Inside a backlog folder: `user-stories.csv` (kind `backlog`), `user-stories/review.csv` (+ `.decided`) and `user-stories/proposals.csv` (kinds `review`, `proposals`), `lexicon.csv` (kind `lexicon`), `lexicon/lexicon-suggestions.csv` (kind `lexicon-suggestions`), `slices/<slice>/`, `context-map.json` and `context-map.md`; slices and the context map are not kinds. Backlogs are named without `.csv` everywhere. The older layout (`backlogs/`, `reviews/`, `proposals/`, `lexicons/`, `lexicon-suggestions/`, `diagrams/`, one file per backlog in each; a `repo.json` it holds is copied but no longer used) is only migrated by copy from the Settings tab, never read as data.
- **`planner/scripts/sync-skill-logic.mjs`**: writes the shared `planner/logic/` files and the guidelines into each story skill's `lib/` and `references/` (see "Story skills" below). **`planner/guidelines/`** (`product-backlog.md`, `sprint-points-guideline.md`, `diagram-conventions.md`) is shown in the portal and copied into the skills. `openspec/` stays at the repo root because the OpenSpec CLI looks for it there.

**`toolkit/`** is the other concern, standalone: reusable Claude Code skills (`skills/`), slash commands (`commands/`: `jois-git`, `jois-init`, `jois-code`, `jois-docs`, `jois-story`), rules (`rules/`) and a PowerShell installer (`install/Install-Toolkit.ps1`) that copies them into `~/.claude` or a project. It depends on nothing above and nothing depends on it; it has its own tests (`cd toolkit; python check_toolkit.py; python -m pytest`, needs Python and pytest, and `node --test <abs>/toolkit/tests/story/*.test.mjs` for the story skills), separate from `npm test`. Its specs live in the root `openspec/` with the rest (`toolkit-*` and `jois-stage`). Install and usage instructions are in `toolkit/README.md`; read that rather than restating it here.

Adding a new tool: see the "Add a new tool" steps in `README.md` (new `planner/portal/web/<tool>/` dir, add to vite inputs, register a kind in `KIND_FILES` of `backlog-paths.cjs`, link from `planner/portal/web/main.jsx`).

## Workflow

Changes are managed with OpenSpec (`openspec/`): `specs/` holds the current capability specs (`csv-file-store`, `user-story-editor`, `toolkit-skills`, ...), `changes/` holds proposals/archives. Use the `opsx:*` skills (propose / apply / archive). Commits use conventional-commit prefixes (`feat:`, `style:`, `chore(openspec):`).

## Story skills

The four story skills are global toolkit items in `toolkit/skills/`: `jois-story-explore`, `jois-story-propose`, `jois-story-review` and `jois-story-plan`. Their commands are `/jois-story:propose`, `/jois-story:re-read` and `/jois-story:review` (`toolkit/commands/jois-story/`). Each carries scripts and a copy of what it shares with the planner, so an installed skill needs nothing from this repo. The specs are `toolkit-story-skills` and the capability specs for each writer.

### Where the data folder comes from

- The scripts use `planner/logic/skill-support/resolve-data-dir.mjs` (copied into each skill).
- Order: the file `PLANNER_CONFIG` names, else `planner.config.yaml` in the current folder or the nearest parent, else the skill asks the user.
- Only `dataDir` is read, from a flat `key: value` file, so no `yaml` package is needed. A relative value is resolved against the config file's folder.

### The generated copy

- `node planner/scripts/sync-skill-logic.mjs` copies the shared logic into each skill's `lib/` and the guidelines into its `references/`. Each copy starts with a `GENERATED from ...` line. The map of what each skill gets is `SKILLS` in that script.
- `planner/test/skill-sync.test.mjs` runs the script into a temp folder and fails when a committed copy differs. After changing `planner/logic/` or `planner/guidelines/`, run the script and commit the copies.
- `planner/logic/diagrams/` was moved into `toolkit/skills/jois-story-plan/diagrams/` and is not copied. Only that skill imports the `mermaid` and `jsdom` packages (`parse-mermaid.mjs`); the portal build and `planner/logic/` never see them.

### How a skill reads and writes

- A skill reads with its reader script (`read-story-context.mjs`, `read-backlog.mjs`, `read-diagrams.mjs`, `read-context-map.mjs`) or ordinary file tools. Nothing confines reading.
- It writes only through a writer script run with Bash. A writer validates everything first (`--check` validates without writing), refuses a path outside the data folder (the target comes from the backlog name and the kind), writes atomically, reads the file back and appends a line to `planner/data/logs/writes.jsonl` (time, writer, backlog, kind, file, bytes, short hash; no contents).
- **Stories are named by Title** with every ID, because IDs shift on `renumber`. `resolveStoryRef` in `planner/logic/backlog/story-ref.js` compares the pair (trimmed, case-folded). The scripts check a Title only when one is given, so each skill's text requires passing it. On a mismatch nothing is written.
- `jois-story-explore` only discusses and never writes. `jois-story-propose` shows full drafts, asks one yes/no and then runs the writers in order: `write-lexicon.mjs`, `write-proposal.mjs`, `write-review.mjs` (and `suggest-lexicon.mjs` for a rename, delete or edit of a term). It reads each file back before it calls anything written.
- `write-proposal.mjs` takes **new stories** (no `id`) and **patches** (an `id` of a proposed story, `NEW-<n>`, plus the fields to change; validation in `proposal-input.js`). It never removes a proposal and never writes `user-stories.csv`. A new story whose Epic, Feature and Title already exist in the proposals is skipped and reported. Clarifications, `resolve` and benching follow the specs `story-proposal-writer` and `story-writing-skills`.
- `jois-story-review` reviews a backlog against `references/product-backlog.md` and writes suggestions to `review.csv` through `write-review.mjs`; it never edits `user-stories.csv`. `read-backlog.mjs <backlog> [section]` serves the context in sections (`guidelines`, `sizing`, `lexicon`, `proposals`, `checks`, `epic-<n>`). Locked stories are reference only.
- `planner/logic/review/review.js` is shared with the portal's Apply and Dismiss, so a suggestion applies the same way in both places.
- Every story has a `Clarifications` column (`Q1: ...` / `A1: ...` pairs, an empty answer is open). A proposed story can be benched (`Benched: Yes`, a column only proposals files have).
- Each backlog has a lexicon, `<backlog>/lexicon.csv`; the rules are in `planner/logic/lexicon/lexicon.js` and `lexicon-suggestions.js`. The skills cite `references/product-backlog.md` and do not restate it.

### The plan skill

- `jois-story-plan` turns the shaped stories of one Epic, Feature or story into a **slice** in `<backlog>/slices/<slice>/`: `UC-<slice>.md` (specification, class diagram, a `### Sequence: <flow>` heading per flow, design sections) and `source.json` (stories by Title and a hash of their text, so a changed, missing or new story shows the slice as stale).
- The rules are in `references/diagram-conventions.md` (a copy of `planner/guidelines/diagram-conventions.md`, the source). Its fenced `diagram-limits` block is read by `diagrams/limits.js`.
- `write-diagram.mjs` runs `checks.js` and Mermaid's own parser on every block, writes nothing when a check fails, and writes `source.json` last. If the skill-local packages are missing it says to run `npm ci` in the skill folder and refuses the write. `Install-Toolkit.ps1` runs that `npm ci` after copying the skill (`-NoPackages` skips it).
- A **context map** (`context-map.json` and `context-map.md`) is read by `read-context-map.mjs` and written by `write-context-map.mjs`; rules are section 9 of the conventions.
- The skill reads the target code base with ordinary `Read` and `Grep` in the current folder. There is no repo setting.




The repo is ESM (`"type": "module"` in `planner/package.json`); `planner/portal/server/server.cjs`, `planner/logic/storage/file-name.cjs` and `planner/logic/storage/paths.cjs` stay CommonJS (the `.cjs` extension), so the server and the ESM skill scripts can share them.

`planner/guidelines/product-backlog.md` is the single source of backlog standards (epic/feature/story/AC definitions, the 13-point size cap, INVEST) used for both writing and reviewing stories; the review skill cites it and does not restate it. `planner/guidelines/sprint-points-guideline.md` covers point sizing benchmarks.
