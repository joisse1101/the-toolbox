## MODIFIED Requirements

### Requirement: OpenSpec setup command
The toolkit SHALL include a command `jois-init:opsx`, the single file
`toolkit/commands/jois-init/opsx.md`, that sets OpenSpec up in the project it runs in. The `/opsx:*`
commands are generated by `openspec` and SHALL NOT be stored or patched by the toolkit. The command
SHALL, asking before each write: run `openspec init` when the project has no `openspec/` folder, and
merge its guidance into `openspec/config.yaml`, which is its one essential write. It SHALL read the
global `workflows` and report it, and SHALL NOT read, set or require the global `delivery`, and SHALL
NOT run `openspec update`, so it works the same whether the `/opsx:*` commands are installed in the
project or globally. It SHALL ask for each write as its own question, in plain words, saying why the
write is needed and whether it affects only this project or every project on the machine. It SHALL be
the only writer of that guidance, and the installer SHALL NOT touch `openspec/`.

#### Scenario: Fresh project
- **WHEN** the command runs in a project with no `openspec/` folder
- **THEN** it SHALL ask, run `openspec init`, then merge the guidance into the new `openspec/config.yaml`

#### Scenario: Existing project with global commands
- **WHEN** the command runs in a project that has `openspec/` and no OpenSpec skills or commands under `.claude/`, because they are installed globally
- **THEN** it SHALL NOT run `openspec init` or `openspec update`, SHALL NOT change `delivery`, and SHALL write only the guidance to `openspec/config.yaml`

#### Scenario: No delivery or update step
- **WHEN** the command runs in any project
- **THEN** it SHALL NOT run `openspec config set delivery` or `openspec update`

#### Scenario: Config has the project's own settings
- **WHEN** `openspec/config.yaml` already has `context`, `rules` or other `operations.*.guidance` entries
- **THEN** the command SHALL keep every one of them and add only its own block

#### Scenario: Re-run
- **WHEN** the command runs again and its block is already in `openspec/config.yaml`
- **THEN** it SHALL replace that block in place, between its begin and end comment markers, and SHALL NOT add a second copy

#### Scenario: Workflows include apply and archive
- **WHEN** the global `workflows` lists `apply` and `archive`
- **THEN** the command SHALL report `workflows=ok` and SHALL NOT ask about the setting

#### Scenario: Workflows missing apply or archive
- **WHEN** the global `workflows` lacks `apply` or `archive`
- **THEN** the command SHALL say in plain words that the commit-stop guidance will not take effect for the missing operation, SHALL offer to fix the global setting as its own optional question that names it as affecting every project, and SHALL NOT change it without a yes

#### Scenario: Each write is asked separately
- **WHEN** the command needs more than one write (init, guidance, optional workflows fix)
- **THEN** it SHALL ask one question per write and SHALL NOT combine them in a single yes/no

#### Scenario: One-line report
- **WHEN** the command finishes
- **THEN** it SHALL print one line stating the OpenSpec version, whether `openspec/` was present, the `workflows` result, whether the guidance was added, replaced or unchanged, and whether the commit rule was found

#### Scenario: Commit rule not installed
- **WHEN** `~/.claude/rules/jois-git-commit-hygiene.md` does not exist
- **THEN** the command SHALL say so and name `Install-Toolkit.ps1`, and SHALL NOT copy the rule itself
