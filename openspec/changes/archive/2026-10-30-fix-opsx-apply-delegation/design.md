## Context

See proposal.md - Why. Constraints that shape the approach:

- `/opsx:*` commands are generated by `openspec` and must not be edited, copied or regenerated. Their
  step 6 says "Make the code changes required" and never mentions an agent.
- OpenSpec skills are not installed here: the workflows are commands in `~/.claude/commands/opsx/`,
  which the Skill tool lists as `opsx:apply` and so on. Getting real skills needs the global
  `delivery` setting and `openspec update`, which `jois-init:opsx` and its spec forbid.
- `opsx-task-applier` has no `Skill` tool. Its hooks block `git commit`, `git push`, `gh` and edits to
  `tasks.md`, which is why it could not run `/opsx:apply` itself: that command ticks boxes and has its
  own commit stop.
- Every command under `toolkit/commands/` is `disable-model-invocation: true`, so a command runs only
  when the user types it. `commands/<folder>/<name>.md` gives `/<folder>:<name>`.
- `check_toolkit.py` lists the command folders that need `metadata.version` and
  `metadata.last_updated` by name (`jois-git`, `jois-init`).

## Goals / Non-Goals

**Goals:**
- Put the delegation procedure in front of the session without relying on a guidance output or an
  installed rule.
- Keep one source for the procedure, and keep OpenSpec state (status, progress, `tasks.md`) in one
  place, the orchestrator.
- Keep agent work aligned with the change's artifacts.

**Non-Goals:**
- Enforcing delegation. Plain `/opsx:apply` still works as before and no hook blocks main-session
  edits: the installer does not manage `settings.json`, and a block needs state about whether an
  apply is running.
- Changing the agent's tools or hooks, `write-pr`, `update-pr` or the commit rule.

## Decisions

**1. The orchestrator is a user-invoked command, `/jois-code:apply <change>`.** The procedure is the
command's text, delivered when the user types it. Alternatives: a guidance line (rejected: the channel
that failed in #43); an always-loaded rule (rejected: loads in every session, and the session can
still prefer the generated command); OpenSpec skills (rejected: not installed, and `delivery` is a
global setting our spec forbids touching).

**2. The command drives the CLI and does not call `/opsx:apply`.** It uses `openspec status` and
`openspec instructions apply --json` for state, `contextFiles`, `context` and `operationGuidance`, and
stops on `blocked` and `all_done` as `/opsx:apply` does. The agent could not run `/opsx:apply` anyway
(decision above), and the orchestrator is the only writer of `tasks.md`.

**3. A group is one `##` section of `tasks.md`, dispatched in file order, one at a time.** A group
with no pending task is skipped; a partly ticked group dispatches only its pending tasks, so a re-run
resumes. Sections are already written as one concern each, which matches the commit stops.

**4. The agent applies a group, with a `result:` clause per task.** It works through the tasks in
order and stops at the first one that is blocked or failed, so no later task is built on it. The
turn limit rises from 30 to 50 because a group holds several tasks.

**5. Alignment comes from the artifacts.** The orchestrator passes the `contextFiles` paths, the
verbatim task texts and the guidance entries that apply; the agent quotes the requirement or scenario
each task satisfies and reports `blocked:` when a task conflicts with the spec, so it never narrows
specified behavior to make a task fit.

**6. The commit stop follows each group.** The command refers to the `jois-git-commit-hygiene` rule by
name and does not restate it. A section that spans several concerns is staged one concern at a time,
as that rule says.

**7. Delegation stays advisory.** Spec and command say so. If sessions still bypass it, the next step
is enforcement (a hook), as its own change.

**8. The setup command stops writing the delegation line.** `jois-init:opsx` keeps the commit-stop
line, loses its agent check and its report field. The agent check moves into `/jois-code:apply`, which
is the only thing that needs the agent.

**9. `check_toolkit.py` lists `commands/jois-code/*.md` as versioned.** The rule entry added earlier
in this change is removed with the rule.

## Risks / Trade-offs

- [A long apply compacts the command's text] -> State lives in `tasks.md` and the CLI, so re-running
  `/jois-code:apply <change>` resumes from the pending tasks.
- [A group is too big for one agent run] -> The agent stops at its turn limit and says what is done
  and what is not; the orchestrator ticks the finished tasks and dispatches the rest.
- [A session runs plain `/opsx:apply`] -> Unchanged advisory behavior; the commit stops still apply
  through the rule and the guidance line.
- [Orchestrator and agent drift on the report shape] -> The command refers to the agent's report and
  `result:` clause by name and does not restate their fields.
- [This repository's `openspec/config.yaml` still holds the old line] -> Replace the managed block as
  a task; re-running `/jois-init:opsx` does the same elsewhere.

## Migration Plan

Additive for users of the new command. Install it with `Install-Toolkit.ps1 -Command jois-code` and
update the agent with `-Agent opsx-task-applier.md`. Re-run `/jois-init:opsx` in each project to drop
the old delegation line from the managed block, and delete `~/.claude/rules/jois-opsx-apply-delegation.md`
where it was installed. To roll back, reinstall the previous toolkit version.
