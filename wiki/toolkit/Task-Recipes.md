# Task Recipes

This page gives the items to run, in order, for seven jobs: starting a repo, doing an OpenSpec change, building a feature from user stories, committing and opening a pull request, writing an issue, taking minutes and setting up the docs. Each recipe names the commands exactly as you type them. What each item does is in the [Toolkit Guide](Toolkit-Guide.md), and how to install them is in [Install](Install.md).

An OpenSpec change is a folder `openspec/changes/<name>/` that holds a proposal, specs, a design and a `tasks.md` task list. It is how this repo plans work before it writes code.

## Start a repo

Run these once in a new repo, in this order. Install the toolkit first, so the commands and the rules exist (see [Install](Install.md)).

1. `/jois-init:opsx` sets OpenSpec up. It runs `openspec init` when `openspec/` is missing and adds the commit guidance to `openspec/config.yaml`. It stops if the `openspec` command-line tool is missing, because it never installs it.
2. `/jois-init:docs` sets the docs process up. Run it second, because it can add archive guidance to `openspec/config.yaml` only when that file exists.

Both commands ask about each write on its own, so you can say no to one write and keep the others. Install `-Rule jois-git-commit-hygiene.md` too: `/jois-init:opsx` reports `commit rule: missing` when it is not installed, and the guidance it adds points at that rule.

## Do an OpenSpec change

The change moves through four steps, and the commit rule applies at the end of each.

1. `/opsx:propose` writes the change's artifacts. These commands are generated by the `openspec` tool, not stored in the toolkit.
2. `/opsx:apply` carries out the tasks.
3. `/opsx:archive` archives the change after review. It follows the commit rule, so it stages by explicit path and waits for the confirmation word.
4. `/jois-git:write-pr` opens the pull request (see the next recipe).

When the change shapes user stories rather than code, the story skills have their own order, described in [Story Skills](../planner/Story-Skills.md).

## Build a feature from user stories

Plan the stories into a slice with the story skills first. Then build, test and document the slice with these commands, in this order. The whole flow, from an idea to the PR, with what each stage writes and how to find the next command after a break, is on [Story to Code](../Story-To-Code.md).

1. `/jois-code:apply slice <backlog>/<slice>` (or `<backlog>/<slice>`, a slice name, a backlog name or nothing, which makes it ask which slice) builds the slice. It checks that the slice is current and stops if it is stale. It then works one `##` group of `tasks.md` at a time and commits each finished group by itself on a branch other than `main` or `master`. On `main` or `master`, or when something is doubtful, it commits nothing, says which condition failed and stops. It ticks the slice's `tasks.md` in place, never stages the slice folder and never suggests `/opsx:archive`. Redraw a stale slice with `jois-story-plan` and run the command again.
2. `/jois-code:validate slice <backlog>/<slice>` tests each acceptance criterion against the running code and writes `validation.md` into the slice folder.
3. `/jois-code:archive slice <backlog>/<slice>` (or `<backlog>/<slice>`, a slice name, a backlog name or nothing, which makes it ask which slice) writes the slice into `wiki/`, one folder per topic, once apply and validate both succeeded at the current commit. It shows every page before it writes and stops at the confirmation word, so the wiki edits are committed with the code. A redrawn slice is archived again by running the command again, which replaces the slice's block in place.
4. `/jois-git:write-pr` opens the pull request.

`/jois-code:apply` needs the agent `task-applier` installed and stops without it. It commits each finished group without testing, reviews the slice with `/jois-code:review` and fixes its findings, and then runs the tests once, as the task in the last group. That task needs `test-runner`: without it the command names the missing agent and stops before the last group. If the session ends, run the command again: it resumes from the tasks not yet ticked. It never pushes.

## Commit and open a pull request

Use these when work is done and sits in the working tree or in local commits.

1. `/jois-git:stage` turns uncommitted changes into one commit per concern. Each commit waits for a confirmation word, and the command repeats until the tree is clean. Skip this step when the commits already exist, for example after `/jois-code:apply`.
2. `/jois-git:write-pr` opens pull requests for the commits since the default branch, grouped by concern. It waits for a confirmation word before it pushes or creates anything. It lists the merge commands in order and never merges.
3. `/jois-git:update-pr` is for later. When the branch gains commits, or the pull request it was stacked on has merged, it pushes, restacks and refreshes the body.

For the Author Verification list, `/jois-git:write-pr` reads the `validation.md` and `review.md` of each slice the branch built, and the test runs it can see in the chat. So for work that is not a slice, run your tests in the same chat before the command.

## Write an issue

1. `/jois-git:write-issue <what you want>` drafts one bug, feature or task issue. Everything after the command is the content of the issue and not an instruction to it.

The command lists similar open issues first, then shows the whole draft, and creates it only when you type its confirmation word. It changes no file in the repo.

## Take minutes

1. `/jois-docs:meeting-minutes` with the notes pasted after it, or a notes file referenced with `@path`.

It asks for every gap, shows the full minutes and saves a file only after you confirm the minutes and the folder. To refine saved minutes, run the command again with the earlier minutes file and the new notes.

## Set up the docs

1. Install the skill folder `jois-init-docs-templates`, in the project or in `~/.claude`. The next command reads every file it writes from there and writes nothing when the folder is missing.
2. `/jois-init:docs` checks the project, then asks one yes or no per write: the checker and builder scripts, the `docs-check` workflow, the pull request checklist line, the `wiki/` starter pages, the publish workflow, the `CLAUDE.md` routing table and the OpenSpec archive guidance.
3. Do the one-time wiki setup that the command states after it adds the publish workflow: enable the wiki, create one first page in the web interface and set the Actions permission to read and write.
4. `python scripts/check_docs.py` runs the checker. It fails on a broken link, a page not linked from `Home.md` or the sidebar, or a path in inline code that does not exist.

The first real publish to the GitHub wiki is unchecked until it runs on GitHub.
