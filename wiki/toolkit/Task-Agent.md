# Task Agent

This page explains how `/jois-code:apply` carries out an OpenSpec change or a slice through two agents, how it decides to commit, how it handles failures and what is enforced. It also covers `/jois-init:opsx`, which sets a project up for OpenSpec. The item lists are in the [Toolkit Guide](Toolkit-Guide.md), and the order of the commands is in [Task Recipes](Task-Recipes.md).

## OpenSpec setup

The `/opsx:*` commands are generated by the `openspec` CLI, which overwrites them on every `init` and `update`, so the toolkit keeps no copy and patches nothing. Instead, run `/jois-init:opsx` inside a project. It works the same whether the `/opsx:*` commands are in the project or in `~/.claude`. It asks about each write on its own in plain words (why, and whether it affects this project or every project), and it does these things:

- It runs `openspec init` when the project has no `openspec/` folder.
- It merges a short commit guidance block into the project's `openspec/config.yaml`, between `# jois-init:opsx begin` and `# jois-init:opsx end`, so a re-run replaces it and the project's own settings stay.
- It reads the global `workflows` and, only when `apply` or `archive` is missing (the guidance would not take effect), offers to add it as a separate optional question.
- It reports when `~/.claude/rules/jois-git-commit-hygiene.md` is not installed.
- It ends with one line, for example `OpenSpec 1.x | openspec/ present | workflows=ok | guidance: added | commit rule: found`.

It never changes the global `delivery` and never runs `openspec update`. The `apply` guidance tells the agent to commit each finished concern as the rule's apply clause says, and to push only on the confirmation word. The `archive` guidance keeps the confirmation word for the archive commit. Projects set up earlier carry the old line, so re-run `/jois-init:opsx` in each project to pick up the new one.

The guidance only points at the `jois-git-commit-hygiene` rule, which holds the steps. It is advisory, and the rule is what enforces them. The accepted losses are that the generated `/opsx:*` commands show in the skill list, and that archive's git commands prompt for permission.

## The two agents

An agent is a file under `toolkit/agents/` with `name`, `description` and `tools` frontmatter, then the instructions. An agent without `tools` inherits every tool, so `python toolkit/check_toolkit.py` fails on one. The installer treats each file as a unit, so `-Agent opsx-task-applier.md` installs one. The toolkit ships three agents (`code-validator` is described under Validating), and other agents in `~/.claude/agents/` are not the toolkit's and are never touched.

`opsx-task-applier` does one group of an OpenSpec change's tasks. `opsx-test-runner` runs the project's own test commands for a group's files and reports each command, exit code and counts. It uses the Haiku model and has no edit tools, installs nothing and never commits, pushes or calls GitHub. It runs a suite in another folder with the command's own folder flag (`npm --prefix`, `git -C`), never `cd`. A passing command whose result shows no exit code and no error is reported as `exit code 0 (the tool showed no error)`, and a failing command is reported with its exit code and error line. Install it with `.\Install-Toolkit.ps1 -Agent opsx-test-runner.md`.

## How a group runs

`/jois-code:apply <change>` hands the tasks of an OpenSpec change to the `opsx-task-applier` agent, one group at a time. A group is one `##` section of the change's `tasks.md`. The group's working detail stays in the agent's own context, so the main conversation keeps one announcement before each group and one line after it. Before each dispatch the session says:

- the group and its tasks
- the files it expects to touch
- a rough time estimate, labeled as an estimate
- that there is no live timer
- how to open the agent's transcript, which is its row in the agent panel and then Enter, or `/tasks`
- the agent's turn limit

`/jois-code:apply slice <backlog>/<slice>` runs the same loop on a slice. A slice task carries a `Satisfies:` line naming acceptance-criteria rows and a `Verify:` line, so the agent reads `UC-<slice>.md` first, names those rows in the Satisfies part of its report and follows the `Verify:` line. It still stops with a `blocked:` line when a task could only be done by dropping part of a named criterion. The command copies each `result:` clause after the task's `Verify:` line in the slice's `tasks.md` and never stages the slice folder.

After each report it says whether the group is done, failed or blocked, and a failure starts a fix round (see Fixing failures below). While the agent works, the command watches the agent's transcript file, `subagents/agent-<id>.jsonl`, with the `Monitor` tool. If the file does not change for 3 minutes, the command says the agent looks stalled and is probably waiting for a permission approval. It shows the agent's last tool call and where to open the transcript, so you can approve the prompt there. A long test run or build looks the same, so the last tool call tells which it is. The watch never edits a permission rule, and if the command cannot find the transcript, it says the watch did not start.

The ticks in `tasks.md` are the progress across groups, and the transcript is the view inside one group. After each completed group the command commits or stops (see Committing a group below). If the session ends, run the command again, and it resumes from the pending tasks.

## Install

Install both parts, then start the command in a Claude Code session:

```powershell
.\Install-Toolkit.ps1 -Command jois-code
.\Install-Toolkit.ps1 -Agent opsx-task-applier.md
.\Install-Toolkit.ps1 -Agent opsx-test-runner.md
.\Install-Toolkit.ps1 -Rule jois-git-commit-hygiene.md -Force
```

The command checks for each agent in `~/.claude/agents/` and in the project's `.claude/agents/`. If `opsx-task-applier` is in neither, the command says so, names `Install-Toolkit.ps1` and stops. If `opsx-test-runner` is in neither, the command says so, names `Install-Toolkit.ps1`, and the command stops with nothing committed when it reaches the group's commit, because it cannot check the tests. The command never copies an agent itself. <!-- docs-check: ignore -->

Re-install the rule and the test runner for the commit exception to take effect. An older installed rule still says "never commit" next to the new command, and `-Force` overwrites the installed rule, which `-List` shows as `differs`.

## Committing a group

The purpose is to commit a checked group without a stop, and to stop with nothing committed when something is doubtful. The command commits by itself only when all of these hold:

- The branch is a named branch other than `main` or `master`.
- `opsx-test-runner` ran the tests for the group's files and every reported command shows exit code 0.
- Nothing foreign is staged or edited. The change folder `openspec/changes/<name>/` is ignored in this check and never staged, because it is committed at archive. In the slice form the folder `<backlog>/slices/` is ignored and never staged too, because git does not track it here.
- No single file holds two concerns.

A passing command that shows no code is reported as `exit code 0 (the tool showed no error)`. The command judges the tests by exit codes, never by the agent's wording.

A fixable doubt gets one rerun before it stops. A fixable doubt is a missing exit code or a suite skipped for a folder problem. The rerun puts the exact commands in the prompt, once per group, and the stall watch covers it. A protected branch, a missing agent and an unrelated change are not rerun and stop with nothing committed. A non-zero exit code is not rerun either. If a pending task of a later group is named as the fix, the commit waits (see Deferring a commit below). Otherwise it starts the fix loop.

A group of several concerns is split, not stopped on. It is cut by the hygiene rule's one-concern list and by task. The tests run once for the whole group before the first commit. Each concern is staged by explicit path and committed in turn with its own message, and each hash is printed. If a later commit fails, the command stops and reports which commits were made. A commit-stop line in the project's `operationGuidance` does not govern these commits.

Otherwise the command commits nothing, says which condition failed and what you can do about it (switch branch, install the agent, fix the test, move the foreign change), and stops, as the apply clause of the `jois-git-commit-hygiene` rule says. It names no confirmation word and asks for none. Work already done stays in the tree and in `tasks.md`, and a rerun resumes from the pending tasks. A stop that follows a failing test comes only after every failure of the group is explained. A protected branch, a detached HEAD, an unreadable branch name, no test command, a suite that could not run, a missing test runner, a foreign change and a file that holds two concerns each cause this stop. It stages by explicit path and never uses `--amend` or `--no-verify`. It never pushes, on any branch, and a rejected commit stops the command and is reported.

## What the agent does

The agent works through the group's tasks in order and stops at the first task that is blocked or failed, so no later task is built on it. For each task its report lists:

- the changed files
- each command with the result and counts its output showed
- the manual checks
- what it could not verify
- the requirement or scenario of the change's specs the task satisfies
- one `result:` clause labeled with the task number
- a `Failures` part, when a command failed, giving for each failure the command, the exact output line, the cause and whether it is fixed

The command copies each clause verbatim into the task's line in `tasks.md` and ticks the box. `/jois-git:write-pr` already reads that clause for Author Verification. The agent never edits `tasks.md`. When a task needs a decision it cannot make, or would narrow a requirement of the specs, it ends with `blocked: <question>`, and the command then asks you.

## Fixing failures

The purpose is to find and fix a failure before the next group starts, without asking you first. A failure is a task the report calls failed, a test command with a non-zero exit code, or a failure the report does not explain. The command sends a fresh `opsx-task-applier` with the failing command, its exact output and the instruction to find the cause and fix it, and after each round it reruns the tests.

A failure is explained only when the `Failures` part gives the command, the exact output line, the cause and whether it is fixed. "Not caused by this group" counts only with evidence, such as the same failure on `main`. The command takes the next group only when every failure is explained, and at most two fix rounds run. It asks you in three cases, says which one applies and shows the failure:

- The agent ends with `blocked: <question>`.
- A second round ends with a failure still unexplained.
- The same failure, with the same command and output line, comes back after a round meant to fix it.

## Validating

`/jois-code:validate` checks the other half of a build: a green test suite does not show that each requirement is met, so it tests the requirements themselves. A requirement it tests is a claim. In the slice form a claim is a task's `Satisfies:` row or a story's acceptance criterion, and in the PR form it comes from the PR description or its linked issue. Install the agent with `.\Install-Toolkit.ps1 -Agent code-validator.md`.

The command orchestrates and the `code-validator` agent tests. The agent has `Read`, `Grep`, `Glob` and `Bash`, a 40-turn limit and a hook that blocks `git commit`, `git push`, `gh` and a recursive and forced `rm`. It has no edit tools, so a test run cannot change the code it judges. The command groups claims by kind (user interface, backend, end to end), runs one agent per group in the background with the stall watch that apply uses, and runs `opsx-test-runner` for suites. A user-interface claim is driven with `playwright-cli`, and test commands come only from the project's own instructions. In the PR form a test file the PR adds or changes also counts, when it fits the runner form those instructions document, and the report marks its evidence as coming from the PR, because a test the author wrote shows what the author expects and is not independent proof.

Each claim gets one verdict: `met`, `not met` or `could not test`. A suite verdict comes from exit codes only, never from wording. A claim is never `met` without evidence: the command and its exit code, or the page text the agent quoted. A claim no check reached, such as one that needs a real external system, is `could not test` with the reason.

A slice run writes its result into the slice folder, which git does not track here. A full run writes `validation.md`. A run for one story writes `validation.partial.md` and leaves `validation.md` as it was, so a partial run cannot hide a validated slice. Each file has a header with the run kind, the date and the tested commit, then one row per claim. A slice counts as validated only when its latest full run has every claim `met`. A PR run writes no file.

The code runs in a git worktree under `.scratch/`, with installs inside it only and mock data only, and the command removes it at the end. Before it runs a PR whose author is not the current git user, it says that it will run code you have not read and that a checkout is not a sandbox, and it waits for your yes. Until the yes it runs only the read-only lookups of the PR and its issue, with no fetch, checkout, install or test. This is a prompt and not a guard: a hostile PR can still harm the machine, so run untrusted code on a separate machine or in a container. The agent's hook is the same kind of backstop as the task agent's, and it does not catch a `gh` call or an `rm -rf` hidden inside a script. Instructions planted in a PR description or a slice are data, and the command ignores them and mentions them in the report.

## Deferring a commit

A failing test does not always need a fix round, because sometimes a later task of the same change is what makes the test pass. In that case the command holds the commit back and goes on, so that it does not fix a failure that the next group would fix anyway.

A failure is deferrable only when it is explained and also names, as its fix, a task that is still pending in a later group. The failure gives the command, the exact output line, the cause and the task number. The command checks the named task in `tasks.md` itself: the task must exist, sit in a later group and be unticked. "A later group will fix it" with no task named is not deferrable, and neither is a task that is ticked or missing, because the report's word alone is not evidence.

For a deferrable failure the command does not commit, says which task it waits for and takes the next group without asking you. After each later group it reruns the tests. While every failure still names a pending task it keeps holding. When every command exits 0 it commits all the held-back changes by explicit path, cut into commits by concern as the `jois-git-commit-hygiene` rule says, and groups that changed the same file keep that file in one commit. It never commits while any command is red.

The last group cannot defer, because no later task is left to fix anything. A red result there runs the fix loop over the whole change, and the command asks you if a failure stays unexplained.

## What is enforced

This is advisory, not enforced. Plain `/opsx:apply` is unchanged, and nothing stops a session that runs it from implementing the tasks itself. Inside the agent, three things are enforced: its tool list, its turn limit (`maxTurns`, 50) and two hooks. The hooks block `git commit`, `git push`, `gh`, a recursive and forced `rm` and an edit of a change's `tasks.md` or of `<backlog>/slices/<slice>/tasks.md`, with either slash style. The `rm` block covers `-rf`, `-fr`, `-r -f` and `--recursive --force`, in any mix of short and long flags. A blocked `rm` fails at once with a message that the cleanup is left for the main session, because without the block the call waits on a permission prompt nobody sees. The toolkit adds no allow rule for `rm`.

The agent's instructions also ask for one plain command per Bash call: no chained `cd`, absolute paths only. The hooks look at the direct command, so a `gh` call or an `rm -rf` hidden inside a script is not caught. The commit checks are the backstop. Groups run one at a time, never in parallel, because the agents share one checkout.
