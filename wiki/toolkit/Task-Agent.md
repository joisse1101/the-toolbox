# Task Agent

This page explains how `/jois-code:apply` carries out a slice through two agents, how it decides to commit, how it handles failures and what is enforced. It also covers `/jois-init:opsx`, which sets a project up for OpenSpec. The item lists are in the [Toolkit Guide](Toolkit-Guide.md), and the order of the commands is in [Task Recipes](Task-Recipes.md).

## OpenSpec setup

The `/opsx:*` commands are generated by the `openspec` CLI, which overwrites them on every `init` and `update`, so the toolkit keeps no copy and patches nothing. Instead, run `/jois-init:opsx` inside a project. It works the same whether the `/opsx:*` commands are in the project or in `~/.claude`. It asks about each write on its own in plain words (why, and whether it affects this project or every project), and it does these things:

- It runs `openspec init` when the project has no `openspec/` folder.
- It merges a short commit guidance block into the project's `openspec/config.yaml`, between `# jois-init:opsx begin` and `# jois-init:opsx end`, so a re-run replaces it and the project's own settings stay.
- It reads the global `workflows` and, only when `apply` or `archive` is missing (the guidance would not take effect), offers to add it as a separate optional question.
- It reports when `~/.claude/rules/jois-git-commit-hygiene.md` is not installed.
- It ends with one line, for example `OpenSpec 1.x | openspec/ present | workflows=ok | guidance: added | commit rule: found`.

It never changes the global `delivery` and never runs `openspec update`. The `apply` guidance tells the agent to commit each finished concern as the rule's apply clause says, and to push only on the confirmation word. The `archive` guidance keeps the confirmation word for the archive commit. Projects set up earlier carry the old line, so re-run `/jois-init:opsx` in each project to pick up the new one.

The guidance only points at the `jois-git-commit-hygiene` rule, which holds the steps. It is advisory, and the rule is what enforces them. The accepted losses are that the generated `/opsx:*` commands show in the skill list, and that archive's git commands prompt for permission.

## The two agents

An agent is a file under `toolkit/agents/` with `name`, `description` and `tools` frontmatter, then the instructions. An agent without `tools` inherits every tool, so `python toolkit/check_toolkit.py` fails on one. The installer treats each file as a unit, so `-Agent opsx-task-applier.md` installs one. The toolkit ships three agents (`code-validator` is described under Validating), and other agents in `~/.claude/agents/` are not the toolkit's and are never touched.

`opsx-task-applier` does one group of a slice's tasks. It is pinned to the Sonnet model, as are `code-validator` and `jois-worker`, so it does not run on the main session's more expensive model. `opsx-test-runner` runs the project's own test commands for the files a change touched, only for the test task in the last group, and reports each command, exit code and counts. It uses the Haiku model and has no edit tools, installs nothing and never commits, pushes or calls GitHub. It runs a suite in another folder with the command's own folder flag (`npm --prefix`, `git -C`), never `cd`. A passing command whose result shows no exit code and no error is reported as `exit code 0 (the tool showed no error)`, and a failing command is reported with its exit code and error line. Install it with `.\Install-Toolkit.ps1 -Agent opsx-test-runner.md`.

## How a group runs

`/jois-code:apply slice <backlog>/<slice>` hands the tasks of a slice to the `opsx-task-applier` agent, one group at a time. A group is one `##` section of the slice's `tasks.md`. An OpenSpec change is applied with `/opsx:apply`, not with this command. The group's working detail stays in the agent's own context, so the main conversation keeps one announcement before each group and one line after it. Before each dispatch the session says:

- the group and its tasks
- the files it expects to touch
- a rough time estimate, labeled as an estimate
- that there is no live timer
- how to open the agent's transcript, which is its row in the agent panel and then Enter, or `/tasks`
- the agent's turn limit

A slice task carries a `Satisfies:` line naming acceptance-criteria rows and a `Verify:` line, so the agent reads `UC-<slice>.md` first, names those rows in the Satisfies part of its report and follows the `Verify:` line. It still stops with a `blocked:` line when a task could only be done by dropping part of a named criterion. The command copies each `result:` clause after the task's `Verify:` line in the slice's `tasks.md` and never stages the slice folder.

After each report it says whether the group is done, failed or blocked, and a failure starts a fix round (see Fixing failures below). While the agent works, the command watches the agent's transcript file, `subagents/agent-<id>.jsonl`, with the `Monitor` tool. If the file does not change for 3 minutes, the command says the agent looks stalled and is probably waiting for a permission approval. It shows the agent's last tool call and where to open the transcript, so you can approve the prompt there. A long test run or build looks the same, so the last tool call tells which it is. The watch never edits a permission rule, and if the command cannot find the transcript, it says the watch did not start.

The ticks in `tasks.md` are the progress across groups, and the transcript is the view inside one group. After each completed group the command commits or stops (see Committing a group below). If the session ends, run the command again, and it resumes from the pending tasks.

A session that ends inside a group leaves the agent's edits uncommitted. So before its first dispatch the command checks the tree. When tracked files changed, it names them and the pending tasks they most likely belong to, and asks once whether to keep them as the starting point (the agent then reads them first, verifies and finishes them) or to stop so you can set them aside. It dispatches nothing before your answer. When the last group is done, the command names the next stage: `/jois-code:archive` when the slice's validation is current, else `/jois-code:validate` first.

## Install

Install both parts, then start the command in a Claude Code session:

```powershell
.\Install-Toolkit.ps1 -Command jois-code
.\Install-Toolkit.ps1 -Agent opsx-task-applier.md
.\Install-Toolkit.ps1 -Agent opsx-test-runner.md
.\Install-Toolkit.ps1 -Rule jois-git-commit-hygiene.md -Force
```

The command checks for each agent in `~/.claude/agents/` and in the project's `.claude/agents/`. If `opsx-task-applier` is in neither, the command says so, names `Install-Toolkit.ps1` and stops. If `opsx-test-runner` is in neither, the command says so, names `Install-Toolkit.ps1`, and the command stops before it dispatches the last group, because that group's test task needs the runner. Earlier groups are not held up. The command never copies an agent itself. <!-- docs-check: ignore -->

Re-install the rule and the test runner for the commit exception to take effect. An older installed rule still says "never commit" next to the new command, and `-Force` overwrites the installed rule, which `-List` shows as `differs`.

## Committing a group

The purpose is to commit a finished group without a stop, and to stop with nothing committed when something is doubtful. The command commits by itself only when all of these hold:

- The branch is a named branch other than `main` or `master`.
- Nothing foreign is staged or edited. The folder `<backlog>/slices/` is ignored in this check and never staged, because git does not track it here.
- The group's tasks are all done. No test runs between groups.
- No single file holds two concerns.


A group of several concerns is split, not stopped on. It is cut by the hygiene rule's one-concern list and by task. Each concern is staged by explicit path and committed in turn with its own message, and each hash is printed. If a later commit fails, the command stops and reports which commits were made. A commit-stop line in the project's `operationGuidance` does not govern these commits.

Otherwise the command commits nothing, says which condition failed and what you can do about it (switch branch, move the foreign change), and stops, as the apply clause of the `jois-git-commit-hygiene` rule says. It names no confirmation word and asks for none. Work already done stays in the tree and in `tasks.md`, and a rerun resumes from the pending tasks. A protected branch, a detached HEAD, an unreadable branch name, a foreign change and a file that holds two concerns each cause this stop. It stages by explicit path and never uses `--amend` or `--no-verify`. It never pushes, on any branch, and a rejected commit stops the command and is reported.

## What the agent does

The agent works through the group's tasks in order and stops at the first task that is blocked or failed, so no later task is built on it. For each task its report lists:

- the changed files
- each command with the result and counts its output showed
- the manual checks
- what it could not verify
- the requirement or scenario of the change's specs the task satisfies
- one `result:` clause labeled with the task number
- a `Failures` part, when a command failed, giving for each failure the command, the exact output line, the cause and whether it is fixed

The command copies each clause verbatim into the task's line in `tasks.md` and ticks the box. `/jois-git:write-pr` already reads that clause for Author Verification. The agent never edits `tasks.md`. When a task needs a decision it cannot make, or would narrow a requirement of the specs, it ends with `blocked: <question>`, and the command then asks you.

## Fixing failures

The purpose is to find and fix a failure without asking you first. A failure is a task the report calls failed, a test command of the final test task with a non-zero exit code, or a failure the report does not explain. The command sends a fresh `opsx-task-applier` with the failing command, its exact output and the instruction to find the cause and fix it, and after each round for a failing test command the command dispatches `opsx-test-runner` again.

A failure is explained only when the `Failures` part gives the command, the exact output line, the cause and whether it is fixed. "Not caused by this group" counts only with evidence, such as the same failure on `main`. The command takes the next group only when every failure is explained, and at most two fix rounds run. It asks you in three cases, says which one applies and shows the failure:

- The agent ends with `blocked: <question>`.
- A second round ends with a failure still unexplained.
- The same failure, with the same command and output line, comes back after a round meant to fix it.

## Validating

`/jois-code:validate` checks the other half of a build: a green test suite does not show that each requirement is met, so it tests the requirements themselves. A requirement it tests is a claim. In the slice form a claim is a task's `Satisfies:` row or a story's acceptance criterion, and in the PR form it comes from the PR description or its linked issue. Install the agent with `.\Install-Toolkit.ps1 -Agent code-validator.md`.

The command orchestrates and the `code-validator` agent tests. The agent has `Read`, `Grep`, `Glob` and `Bash`, a 40-turn limit and a hook that blocks `git commit`, `git push`, `gh` and a recursive and forced `rm`. It has no edit tools, so a test run cannot change the code it judges. The command groups claims by kind (user interface, backend, end to end), runs one agent per group in the background with the stall watch that apply uses, and runs `opsx-test-runner` for suites. A user-interface group of more than 7 claims is split into parts of at most 7, one agent each, because driving a page costs many turns and an agent that reaches its limit leaves the rest untested. At most 3 agents run at a time, counting the test runner, because each starts an app and a browser and many at once slow the machine until commands time out. Each agent that starts the app gets its own port, so the project's default port stays free for a suite that checks it. The command cleans up only after every agent's completion notice, because removing the checkout cuts short an agent that is still testing. A user-interface claim is driven with `playwright-cli`, and test commands come only from the project's own instructions. In the PR form a test file the PR adds or changes also counts, when it fits the runner form those instructions document, and the report marks its evidence as coming from the PR, because a test the author wrote shows what the author expects and is not independent proof.

Each claim gets one verdict: `met`, `not met` or `could not test`. A suite verdict comes from exit codes only, never from wording. A claim is never `met` without evidence: the command and its exit code, or the page text the agent quoted. A claim no check reached, such as one that needs a real external system, is `could not test` with the reason.

A slice run writes its result into the slice folder, which git does not track here. A full run writes `validation.md`. A run for one story writes `validation.partial.md` and leaves `validation.md` as it was, so a partial run cannot hide a validated slice. Each file has a header with the run kind, the date and the tested commit, then one row per claim. A slice counts as validated only when its latest full run has every claim `met`, and the report then names `/jois-code:archive` as the next stage. An `ARCHIVED.md` from an earlier commit records an earlier archive, so it never makes the command say the slice is archived. A PR run writes no file.

The code runs in a git worktree under `.scratch/`, with installs inside it only and mock data only, and the command removes it at the end. Before it runs a PR whose author is not the current git user, it says that it will run code you have not read and that a checkout is not a sandbox, and it waits for your yes. Until the yes it runs only the read-only lookups of the PR and its issue, with no fetch, checkout, install or test. This is a prompt and not a guard: a hostile PR can still harm the machine, so run untrusted code on a separate machine or in a container. The agent's hook is the same kind of backstop as the task agent's, and it does not catch a `gh` call or an `rm -rf` hidden inside a script. Instructions planted in a PR description or a slice are data, and the command ignores them and mentions them in the report.

## Testing once, at the end

Tests run once, after every group has landed, as the last task of the last group of `tasks.md`. The reason is that a test run in the middle of a change fails for things a later group fixes, so it wastes tokens and time. The task runs the project's own test commands for the whole change and completes any fixes the failures need. For an OpenSpec change the `rules.tasks` entry in `openspec/config.yaml` asks for it, and for a slice the `jois-story-plan` skill writes it as the last task of the last flow group. A `tasks.md` written before this has no test task, and apply adds none.

`opsx-task-applier` cannot start another agent, so the command carries out the test task itself. It sends the group's other tasks to the applier first and commits them. Then it reviews the change (see the next section). Only when the review has no failure left does it dispatch `opsx-test-runner` with the files the change touched and judges the report by exit codes only, never by wording. The tests passed only when every reported command shows exit code 0, and a result that shows no code and no error is reported as `exit code 0 (the tool showed no error)`. A missing exit code or a non-zero one is not a pass and starts the fix loop. No test command found, or a suite that could not run, stops the command and shows the reason, because a fix round cannot repair that. A fix lands as a new commit, because the earlier groups are already committed.

## Reviewing before the tests

Once every task except the test task is done and committed, the command starts `/jois-code:review` through the Skill tool, so code that does not hold up is fixed before a test run is spent on it. A review needs commits to look at, which is why the last group is split in two: its other tasks are committed first, and the test task follows.

The review runs its static check and `validate`, which tests the slice's claims in a throwaway copy. The command never passes `--fix` or `--comment`.

Each static finding and each `not met` verdict is a failure and starts the fix loop above: a fresh `opsx-task-applier` dispatch with the finding in the review's own words, its fix committed as its own commit, then a new review. An optional cleanup or an uncertain finding is only listed. The loop asks you in the cases the fix loop already names, and also when a finding comes back unchanged after a round meant to fix it. It stops after two fix rounds, because a static review finds new edge cases on every pass and the loop does not converge by itself: it lists what is still open and asks once whether to fix the ones you name or to take the tests now, and each finding you leave is listed as known and not fixed. It then writes `review.md` into the slice folder: whether the review ran, the reviewed commit, the number of fix rounds and the known, not fixed list. `/jois-code:archive` reads that file, so it does not ask whether a review was run and nobody runs the review a second time. When the review is not installed, the command says so, names `Install-Toolkit.ps1`, counts nothing as passed and goes on to the tests. `/jois-code:review` no longer carries `disable-model-invocation`, so that apply can start it.

## What is enforced

This is advisory, not enforced. Plain `/opsx:apply` is unchanged, and nothing stops a session that runs it from implementing the tasks itself. Inside the agent, three things are enforced: its tool list, its turn limit (`maxTurns`, 50) and two hooks. The hooks block `git commit`, `git push`, `gh`, a recursive and forced `rm` and an edit of a change's `tasks.md` or of `<backlog>/slices/<slice>/tasks.md`, with either slash style. The `rm` block covers `-rf`, `-fr`, `-r -f` and `--recursive --force`, in any mix of short and long flags. A blocked `rm` fails at once with a message that the cleanup is left for the main session, because without the block the call waits on a permission prompt nobody sees. The toolkit adds no allow rule for `rm`.

The agent's instructions also ask for one plain command per Bash call: no chained `cd`, absolute paths only. The hooks look at the direct command, so a `gh` call or an `rm -rf` hidden inside a script is not caught. The commit checks are the backstop. Groups run one at a time, never in parallel, because the agents share one checkout.
