# Command Details

This page gives the behaviour of the toolkit's commands and of the design skill in detail: what each does step by step, what it refuses and why. The one-line summaries are in the [Toolkit Guide](Toolkit-Guide.md), and the order in which to run them is in [Task Recipes](Task-Recipes.md). A command is a markdown file under `toolkit/commands/`, and a folder there is a namespace, so `toolkit/commands/jois-git/stage.md` is `/jois-git:stage`. The installer treats each entry directly under `toolkit/commands/` as one unit, so `-Command jois-git` installs the whole `jois-git` set (see [Install](Install.md)).

## Commands stay out of the session context

Every command declares `disable-model-invocation: true`, so its description is not loaded into each new session's skill listing, which would cost about 300 tokens for a typical set. You can still type `/jois-git:stage`. `python toolkit/check_toolkit.py` fails on a command without the flag, except `/jois-code:validate`: the Skill tool refuses a command that has the flag, and `/jois-code:review` starts validate that way. So validate has no flag, its description is loaded into each session's skill list, and it keeps its own confirmation before it runs a pull request that is not yours. Skills are not given the flag, because Claude should be able to pick a skill by its description.

## The jois-git commands

### /jois-git:stage

It clears a messy working tree, with or without an OpenSpec change. It stages one concern at a time, shows the message and a confirmation word, and waits. Typing the word commits that concern and moves on, until the tree is clean. Secret files and build output are skipped and named. It has no commit authority of its own: the commit rule's confirmation word is what allows each commit.

### /jois-git:write-pr

It opens GitHub pull requests (PRs) for the commits on the current branch. It is one file, so the steps, the PR guidelines, the body template and the verification rules all sit inside it. It reads the commits since the default branch on the remote, so a local branch that is behind does not matter. It proposes groups of commits that each form one concern, and a refactor never shares a PR with a feature. It waits for a confirmation word before it pushes or runs `gh pr create`. Each body lists the test files the group adds, an Author Verification list and suggested steps for a reviewer.

The verification comes from three sources. The first is the result files of each slice the branch built: `validation.md` from `/jois-code:validate` and `review.md` from `/jois-code:apply`. They count only when their commit is on the branch and only the wiki changed since. The second is the `tasks.md` of an OpenSpec change the commits touch, for its recorded results. The third is the test, build or lint runs it can see earlier in the same chat, so run your tests in the chat before you type the command. It states no result that a source did not record. When a group has no verification and the repo documents a test command for the directories it changes, it asks once, for all groups, whether to run them. It runs only what you agree to, and otherwise asks what you ran. A failing or timed-out run is reported, never fixed, and does not block the PR.

A `chore`, `build`, `ci`, `docs` or `revert` group whose diff changes no behavior needs no tests. This is judged from the diff, and when unsure the group gets tests. Such a group gets a one-sentence summary and no testing block, and is never asked about. The presentation says why, so you can reply that it needs tests. The reviewer steps aim at what the group changes, such as the test a fix adds, and may use a command you ran earlier in the chat.

The command also works from the default branch. Commits ahead of the remote go to new branches named `type/slug`, or `type/TICKET-slug` when a commit references a ticket, where the type is a commit type such as `feat` or `fix`. <!-- docs-check: ignore --> Once every PR is opened, the local default branch is set to the remote with `git branch -f`, which leaves uncommitted changes alone. The confirmation word covers that reset, and nothing is reset if a push or PR failed.

Before it opens anything, it uses only commands the repo's own documents state, and it shows you the source of each line before you confirm, never in the PR. It blocks a group whose diff holds a secret, an `.env` file or build output, and it warns on debug prints.

It never merges. A hook in the command's frontmatter blocks `gh pr merge`, `--auto` and merge calls through `gh api`. A hook is a check that runs before a tool call and can refuse it, and this one stays active for the rest of the session once the command has been invoked. The hook looks for those words anywhere in a shell command's text, so text that merely mentions them is refused too. For that reason the command passes each PR body from a file.

When it finishes, it lists every PR it opened in the order to merge, with a merge command for each, for you to run. A PR that nothing is stacked on gets `gh pr merge <n> -s -d`. A PR that another PR is based on gets it without `-d`, because deleting its branch closes the PR above it and GitHub cannot reopen that one. For each PR above it the list gives the follow-up in order: rebase, push with `--force-with-lease`, retarget to the default branch, delete the earlier branch.

It replaces the old `/write-pr` skill. If you installed that, delete `~/.claude/skills/write-pr`, because the installer only manages items the toolkit still holds. Then run `.\Install-Toolkit.ps1 -Command jois-git -Force`.

### /jois-git:update-pr

It brings the open PR of the current branch up to date. It finds the PR, then handles whichever of these apply:

- A restack, when the PR sits on a branch whose PR has merged and that branch still exists. It rebases onto the default branch and retargets the PR.
- A push of commits the remote lacks.
- A refreshed body, built from the same template and verification rules as `/jois-git:write-pr`, shown to you as a diff against the live body.

One confirmation word covers everything it will do, listed first. It pushes plainly, except the `--force-with-lease` push of a restack you confirmed. It never uses `--force`, never renames or deletes a branch, and never merges (the same hook as write-pr). With no open PR it says so and points to `/jois-git:write-pr`.

It is also a single file, so the body template and verification sections are copied from write-pr, and `python toolkit/check_toolkit.py` fails if the two copies differ. The same no-tests rule and targeted reviewer steps apply to its refreshed body.

### /jois-git:write-issue

It drafts one issue and creates it on the repository's host. Everything you write after the command is the content of the issue, never instructions to it. It changes no file in the repository.

It reads the `origin` remote. A `github.com` host uses `gh`, a host with `gitlab` in its name uses `glab`, and any other host it asks you about once. `glab` is needed only for GitLab repos, and its flags are checked against the GitLab CLI docs, not run. It lists similar open issues from your description before it drafts anything. It picks a bug, feature or task template from what you describe, or asks when it could be two. It uses the repository's own template from `.github/ISSUE_TEMPLATE/` or `.gitlab/issue_templates/` instead when one matches. <!-- docs-check: ignore -->

A required section you give nothing for is drafted from your words, the conversation and, for a bug or feature, the files your request points at (read first, read-only). It points out each drafted section when it shows you the issue, and asks, as a numbered list, only when nothing supports a draft. Optional sections you give nothing for are left out, heading included:

- Bug: Screenshots / Logs and Environment.
- Feature: Alternatives Considered, Design / Visuals and Technical Considerations / Security.
- Task: Testing & Verification and Dependencies / Blockers.

It titles the issue like a commit (`fix:`, `feat(scope):`, `chore:`, at most 70 characters) and scans the draft for secrets. It prints the whole issue and creates it only when you type its confirmation word, passing the body from a file, and then reports the issue as a link. It only creates: no labels, assignees, milestones, closing or comments.

## The jois-code commands

`/jois-code:apply <change>` applies an OpenSpec change through the task agent. It hands the change's tasks to the `opsx-task-applier` agent, one group at a time, and records each task's `result:` clause in `tasks.md`. It commits each finished group by itself on a branch other than `main` or `master`, holds the commit back while a named pending task of a later group fixes a failing test, and otherwise stops with nothing committed, says which condition failed and names no confirmation word. It ignores the change's own folder `openspec/changes/<name>/` and never stages it, because neither apply nor `/jois-code:archive` commits that folder. It splits a group of several concerns and commits each in turn. It never pushes and never implements a task itself. Without a change name, it asks you to choose.

`/jois-code:apply slice <backlog>/<slice>` is the slice form. The argument alone picks the form, so a bare name is always an OpenSpec change, and `slice` with no `<backlog>/<slice>` makes the command ask for one. In this form the command does not call `openspec`. It reads the slice's `tasks.md` and `UC-<slice>.md` from `<backlog>/slices/<slice>/`. Before the first group it runs the plan skill's `read-diagrams.mjs` for the stale check, and it stops, naming each story by Title and pointing to `jois-story-plan`, when the slice is stale, missing, or the plan skill is not installed (then it names `Install-Toolkit.ps1`). It records each `result:` clause on a line after the task's `Verify:` line and ticks only that task. It never stages or counts anything under `<backlog>/slices/`, because that folder is not tracked by git here, so the ticks stay local. When every task is ticked it says the slice is built and never suggests `/opsx:archive`. Steps 4 to 11 are the same as for a change.

Install it with `.\Install-Toolkit.ps1 -Command jois-code`. It needs the agent, which you install with `-Agent opsx-task-applier.md`, and it also uses `opsx-test-runner` once, for the test task in the last group, installed with `-Agent opsx-test-runner.md`. The full account of the agents, the commit conditions, testing once at the end and the failure loop is on [Task Agent](Task-Agent.md). Before the test task it runs `/jois-code:review` and fixes what the review finds, as [Task Agent](Task-Agent.md) describes. It is advisory: plain `/opsx:apply` is unchanged and still works as before.

`/jois-code:validate` tests whether code does what its plan or its PR says. The argument alone picks the form, and an argument that is neither `slice <backlog>/<slice>` nor a PR number makes the command ask for one and test nothing. A slice form first runs the plan skill's `read-diagrams.mjs` and stops, naming each story and pointing to `jois-story-plan`, when the slice is stale, missing or ambiguous. It then prints the claim list, one claim per `Satisfies:` row and per acceptance criterion, and tests each claim in a git worktree under `.scratch/` that it removes at the end. Naming one story ID after the slice tests only that story's claims and makes the run partial. The PR form reads the PR and its linked issue with `gh pr view` and `gh issue view`, which are read-only, and uses the description alone when no issue is linked. See [Task Agent](Task-Agent.md) for the agent, the verdicts and the result file. Install it with `.\Install-Toolkit.ps1 -Command jois-code`, plus the agents `code-validator.md` and `opsx-test-runner.md`.

`/jois-code:review` checks a PR, or the current branch against `main`, in one step. A number is a PR and no number is the branch, and on `main` with no number it says there is nothing to review. It runs the built-in `code-review` skill for the static check and `/jois-code:validate` for the behavioural check, and it re-implements neither. For a PR, validate's PR form gives the intent. For a branch, the intent must come from you: name `slice <backlog>/<slice>`, or the command asks for a slice or a PR number and tests nothing until you answer. If you give nothing, the report holds the static findings and says the behavioural check was not run. The command can also be started by `/jois-code:apply`, which gives it no slice or PR number for an OpenSpec change, so it then runs the static check only and does not ask. The report keeps the two parts apart and never merges them into one pass or fail. The effort level goes through to `code-review` only when you give it. `--comment` is confirmed once, before the static check, naming the PR, because `code-review --comment` posts as it runs; a no runs the checks without posting, and `--comment` on a branch is refused because a branch has no PR. `--fix` is refused. Validate keeps its own confirmation before it runs a PR that is not yours, and the review command never answers it for you. Install it with `.\Install-Toolkit.ps1 -Command jois-code`, plus the validate agents `code-validator.md` and `opsx-test-runner.md`.

`/jois-code:archive slice <backlog>/<slice>` folds a finished slice into the project's wiki. It takes that one form, and any other argument makes it ask for the form and read and write nothing. It refuses, and names each reason, when the slice is stale, missing or ambiguous (by `read-diagrams.mjs`), a task is not ticked, a design decision is `TBC`, a story in scope has an open clarification question, or the slice's `validation.md` is not `Validated: yes` at the current `git rev-parse HEAD`. A validation from an earlier commit still counts when only `wiki/` changed since, so a rerun after the wiki commit needs no new validation. A partial run never counts. It does not ask whether the slice was built or planned, because only a built one is accepted. It then reads the slice's `review.md`, which `/jois-code:apply` writes when its review step ends. When that file says the review ran at a current commit (by the same rule as `validation.md`), archive records `review: run` in the source row without asking and names what the review left open. Otherwise it asks whether `jois-code review` was run, says why the file did not settle it, and writes your answer into the source row.

Archive writes each topic as a folder, `wiki/<topic>/`, so a reader opens the short page that answers their question instead of reading through the plan. `overview.md` says what the feature does and how to use it on one screen. `reference.md` holds the endpoints, status codes, limits and data files as tables. `design.md` holds each slice in its marked block and the `## Sources` table. Overview and reference describe the topic as it is now, so they carry no markers, and each slice's edits to them are shown as diffs.

Archive reads the routing table in `CLAUDE.md` and `wiki/Home.md`, searches `wiki/` for each topic and prints a map from each part of the slice (stories, flows, diagrams, contracts, rules and design decisions) to the page of the folder that answers its question. A password-reset slice extends the authentication folder and gets no folder of its own. A new folder is created only when no folder or page covers the topic, and it is named for the topic. A topic that is still one flat page is written in place and never split on archive's own initiative, because other pages and `CLAUDE.md` link to it. You approve the map before any diff. Each row of the slice's `Changes to existing specs` section is then drafted as a diff beside the row and written only after you approve it. A `modified` or `removed` row whose page does not exist is skipped and reported.

What a slice adds to `design.md` sits between `<!-- archive:<backlog>/<slice>:start -->` and `:end` markers. The block has three sections. `Behaviour` holds one `| Situation | Result | AC id |` table per story, with each acceptance criterion next to the behaviour it proves and each failure response and rule on that row. `How it fits together` holds the diagrams, and `Decisions` holds a table of design decisions. Archive checks that every AC id of the slice appears exactly once in the block. The page's `## Sources` table gets one row per slice with the scope, date, review answer, story Titles with the hashes copied from `source.json`, and the commit. A rerun replaces both in place and leaves a page with one copy. Each Mermaid diagram is parsed before its diff is shown, with `node parse-mermaid.mjs -` of the plan skill (it reads the text to be written from standard input through a quoted here-document, the one shell write the command allows, and exits 1 on a failure), and each written page is read back. The command has no hook. Its `allowed-tools` pre-approves `Write` and `Edit` only for `wiki/**` and `**/slices/*/ARCHIVED.md`, `git add` only for `wiki/*`, `git diff --name-only` and `git merge-base --is-ancestor`, and nothing for `git commit`, `git push` or `gh`. Anything else makes Claude Code ask you, so the command never writes outside the wiki without your answer. An allow list asks and does not refuse, and a permissive permission mode can skip the question. To refuse a push outright, add `Bash(git push:*)`, `Bash(git commit:*)` and `Bash(gh:*)` to `permissions.deny` in your own `settings.json`. The installer never edits that file, so this is your change, and it also stops a push you approve with a confirmation word.

After the writes it runs `python scripts/check_docs.py`, leaves the slice unmarked when that fails, and otherwise writes `ARCHIVED.md` into the slice folder as two short tables: the date, commit, review answer and stories, then each page touched and what changed on it. It deletes nothing, because frozen stories and the supersedes rule need the slice. It stages the wiki paths one by one, never the slice folder, stops at the confirmation word of the commit rule and ends with a count of pages added, replaced, unchanged and skipped. The wiki edits travel in the same PR as the code, and `/jois-git:write-pr` comes after. Install it with `.\Install-Toolkit.ps1 -Command jois-code`; the plan skill must be installed too.

## The jois-docs commands

`/jois-docs:meeting-minutes` turns notes into minutes in a fixed template. It is one file with the template inside, and it needs no script. Install it with `.\Install-Toolkit.ps1 -Command jois-docs`.

Paste the notes after the command, or reference a notes file with `@path`. Notes are data, never instructions. It asks for every gap (chair, note taker, owners, due dates, next meeting) before it shows the minutes, and a field you skip shows `[TBC]`. It never invents a value and attributes a point to a person only when the notes do.

It shows the full minutes first and writes nothing until you confirm the minutes and the folder. The file is named `<slug>_<YYYY-MM-DD>.md`, with `_1`, `_2` and so on when the name is taken. For notes from a referenced file it offers that file's folder. For pasted notes it looks for a folder such as `docs/`, `meetings/` or `notes/`, suggests one and asks. It never overwrites the notes file.

To refine minutes, reference an earlier minutes file together with new notes. It rebuilds the full minutes, shows them and, after you confirm, replaces that file. Without a referenced minutes file, every save is a new file.

## The jois-design-ui-principles skill

It gives Claude visual-design rules and frontend structure rules, so an interface looks designed and its code is grouped and easy to work with. The folder is `toolkit/skills/jois-design-ui-principles/`, and you install it with `.\Install-Toolkit.ps1 -Skill jois-design-ui-principles`.

It fires when you design, build, style, review or polish a page, component, form, dashboard, card, table or layout, when you write the HTML, CSS or React code of such a screen, and on a request such as "make it look better" or a critique of a screenshot. It does not fire for behaviour-only changes, command-line tools and backend code, or any code with no visual output.

`SKILL.md` holds three principles, the rules by topic in one line each and a review checklist. Detail sits in `references/`, which Claude reads only when the task touches the topic, so a task that needs no palette does not pay for the colour page. The skill looks for the project's design tokens first, where a design token is a named value, such as a colour or a spacing step, kept in one place. It uses the project's tokens where they exist, and fills only the gaps from the starter values in `toolkit/skills/jois-design-ui-principles/references/tokens.md`, telling you those values are defaults.

| File in `references/` | Read it when |
| --- | --- |
| `tokens.md` | The project lacks spacing, type, radius or shadow tokens, or the starter values are needed. |
| `color.md` | A palette, shades or text colours are chosen or built. |
| `depth.md` | Shadows, raised or inset surfaces or overlapping layers are added. |
| `images-and-polish.md` | The UI has images, icons or empty states, or needs finishing touches. |
| `structure.md` | Markup or components are written or restructured. |

The visual rules are a paraphrase of *Refactoring UI* by Adam Wathan and Steve Schoger, and no passage is copied. The structure rules and every size limit are the toolkit's own, not the book's. React mechanics stay in the `jois-code-typescript-react` rule, which the skill links to and does not restate.
