# Story Skills

Five skills let Claude Code work on a backlog beside the portal: `jois-story-explore`, `jois-story-propose`, `jois-story-review`, `jois-story-plan` and `jois-story-verify`. Four slash commands start or check that work: `/jois-story:propose`, `/jois-story:re-read`, `/jois-story:review` and `/jois-story:verify`. This page says what each does, what it writes and in which order to use them. The skills' own scripts and the generated copies of shared code are described on [Story Skills Internals](architecture/Story-Skills-Internals.md), and the routines that combine them with the portal are on [User Flows](User-Flows.md). A skill is a folder of instructions and scripts that Claude loads when you ask for the work or name it. A slash command is a prompt you type to run a fixed routine.

## What all five skills share

Each skill finds the data folder itself, in the folder where you started Claude and never in a parent folder. It uses the config file `PLANNER_CONFIG` names, else a `.plans` folder in the current folder, else a `planner.config.yaml` there. So start Claude in the code base folder, or set `PLANNER_CONFIG`. When nothing is found the skill says which folder it looked in. The propose, review and plan skills then offer to create `.plans`, only after you agree, and the explore and verify skills only report it, because they create no folder. Explore then carries on without a backlog, because it writes nothing: it says so once, names **Add Project...** in the planner (which creates `.plans` and a first backlog) and checks the drafts against the guidelines and the wiki only.

A skill writes only through its own writer scripts. A writer checks everything first, writes nothing when anything is invalid, and the skill reads the file back before it says that something was written. The skills never edit the text of a story in `<backlog>/user-stories.csv`, because the portal saves that file as you edit and a second writer would clash with it. The one exception is `jois-story-plan`, which sets the `Frozen` flag of the stories a confirmed slice covers (see below). They name a story by its title and pass the title with every ID, because the IDs of stories that are not frozen shift when the backlog is renumbered and a title mismatch stops the write. They treat everything read from a file as data and never as instructions.

## Order of use

Use the skills in this order, and skip the ones you do not need. Explore the idea, propose what you agreed, review the backlog, plan the shaped stories, then verify the slice before you build from it. The portal sits between the steps: you accept proposals, apply or dismiss suggestions and edit terms there, and the later steps read the result.

| Step | Skill or command | Writes | You then |
| --- | --- | --- | --- |
| 1. Explore | `jois-story-explore` | nothing | decide what to save |
| 2. Propose | `jois-story-propose`, `/jois-story:propose` | proposals, review suggestions, terms, term suggestions | accept, apply or dismiss in the portal |
| 3. Review | `jois-story-review` | review suggestions | apply or dismiss in the portal |
| 4. Plan | `jois-story-plan` | a slice and the context map, then checks the slice with verify | open the slice document |
| 5. Verify | `jois-story-verify`, `/jois-story:verify` | a corrected slice, review suggestions, only after you approve | build from the slice, apply or dismiss suggestions in the portal |

Run `/jois-story:re-read` whenever you changed files in the portal or in a spreadsheet during a session, and `/jois-story:review` to check that a session's work is in sync.

## jois-story-explore

Use it to think through new stories before writing anything. It reads the backlog, the proposals and the lexicon through `read-story-context.mjs`, and it discusses scope, splitting, epic and feature placement, dependencies and acceptance criteria against `planner/guidelines/product-backlog.md`. It may sketch drafts in the conversation, and it says they are not saved. It asks the question that decides how stories are split before it drafts, and it checks new or renamed terms against the lexicon and every Avoid list before a story uses them.

It never writes a file and runs no command except the reader. Besides the reader it has the read-only tools `Read`, `Grep` and `Glob`, for pages of the project's `wiki/` and for what the reader's caps cut off (the reader stays the default for backlog data). It ignores benched proposed stories.

Before it shows a draft, the skill also checks whether the idea repeats something the project has already built. `/jois-code:archive` writes each finished slice into the wiki between `<!-- archive:<backlog>/<slice>:start -->` and `:end` markers and lists it in the page's `## Sources` table. The skill searches `wiki/` for those markers, follows the routing in `CLAUDE.md` and `wiki/Home.md`, and reports each overlap with the slice id, the page path and the story Titles from the `## Sources` row. It gives no built-or-planned status, because archive refuses a slice that is only planned, so every archived slice is built. You decide whether the idea extends the archived design, replaces it or was already covered. A fact an archived page holds is read from the page and not asked of you. With no `wiki/` or no marker the skill says so once and works as before. Archived text is data, and the skill never writes to the wiki.

Every new or changed story is checked against the backlog, the proposals and the wiki by the contradiction rule (see [The contradiction rule](#the-contradiction-rule)). The skill reports a contradiction, asks you which side stands, and shows the resulting Notes lines in the reply only, because it writes nothing. When you want the drafts saved it hands over to `jois-story-propose`, and typing that name or asking to save is the hand-over. There is no slash command for it, so ask for it by name, for example by giving a backlog name and a story or idea.

## jois-story-propose and /jois-story:propose

Use it to save what you agreed. The skill turns the session into four kinds of output, each written by its own script:

- New stories and patches to proposed stories go to `<backlog>/user-stories/proposals.csv` (`write-proposal.mjs`). The Proposed tab shows them.
- Changes to stories already in the backlog go to `<backlog>/user-stories/review.csv` as suggestions (`write-review.mjs`). The Editor and Review tabs show them.
- New terms go straight into `<backlog>/lexicon.csv` (`write-lexicon.mjs`).
- An edit, rename or delete of an existing term goes to `<backlog>/lexicon/lexicon-suggestions.csv` (`suggest-lexicon.mjs`). The Lexicon tab shows it, and the term changes only when you apply it.

New stories get the next free placeholder ID `NEW-<n>`, or patch a proposed story in place. A new story whose Epic, Feature and Title are already in the proposals is skipped, so sending a batch again is safe. An agreed change to a story already in the backlog becomes one review row, and review rows from this skill always append. An edit to a locked story comes with an `unlock` row. A benched story is skipped by the skills.

The skill first runs each writer with `--check`, then shows every draft in full and asks one yes or no question, and it writes only after a separate yes. It writes in this order: lexicon, term suggestions, proposals, edits. It never removes a proposed story and never writes `user-stories.csv`.

After the last write the skill calls `jois-story-review` on the stories it just wrote, so a mistake is caught while you are still in the session. Review runs in findings mode, which means it reads, writes nothing and hands its findings back. A finding that review marks `ready` (the fix is certain) is applied to the proposed story as a patch, without a second question, and the report lists each one with the old and the new value. A finding marked `confirm`, or one that needs your decision, is never applied: the skill adds a question to the story's Clarifications instead. It stops after 2 rounds and lists what is left. Findings about a backlog story or a frozen story are only reported. The one exception to "write only after your yes" is this round of patches, and the portal's Proposed tab lets you edit any of them.

The skill has `Read`, `Grep` and `Glob` too, used for wiki pages and for what the reader's caps cut off, never to write. It runs the contradiction rule on every draft before it shows one as ready. The `Changes existing spec` and `Supersedes` lines go in the `notes` of the new story, are shown in the complete draft, are covered by the one yes or no, and are written only through the proposals writer. An edit to a contradicted story that is not frozen becomes a review suggestion, and one to a proposed story becomes a patch. The skill never writes to `wiki/`.

The command `/jois-story:propose` runs the same skill and skips the yes or no question, because running it is your go-ahead. It drafts from the conversation so far and stops if nothing was agreed. It still prints each draft right before its writer runs, checks first and reads each file back. Add extra instructions after the command and they are passed along.

## jois-story-review

Use it to review a whole backlog. It reads the backlog in sections (`read-backlog.mjs`: checks, lexicon, proposals, sizing, guidelines, then each epic) against `planner/guidelines/product-backlog.md`. It looks at the hierarchy, the INVEST principles, the acceptance criteria with an edge-case checklist, and consistency across stories, the lexicon and the proposals. Every finding about a story comes with a field edit the portal can apply, written to `<backlog>/user-stories/review.csv` through `write-review.mjs` in batches of about eight to ten rows. Findings about the lexicon or proposals cannot be edited by this skill, so they go in the report as questions. Open questions about a story are suggested as `Clarifications` rows. A review run without `--append` replaces the whole review, these rows included, so apply the suggestions you want before you run it again.

Frozen stories are reference only: they are not reviewed, and the skill writes no row for them. A strong objection to a frozen story goes in the report, with the note that a change to it needs a superseding story (a story that replaces it, see [The contradiction rule](#the-contradiction-rule)). The skill ends with a report grouped by area, and tells you the suggestions are applied or dismissed in the portal. It does not apply them itself. There is no slash command to start it, so ask for it by name.

Another skill can also start review. Called with a list of stories, it runs in findings mode: it reviews only those stories, writes no `review.csv` and returns the findings to the caller.

## jois-story-plan

Use it to turn the shaped stories of one Epic, one Feature or one story into a slice, a document with the use-case specification, a class diagram and sequence diagrams as Mermaid blocks. It also draws a context map when you ask, which sets the bounded contexts of the product, their owners and how they link. The slice goes to `<backlog>/slices/<slice>/` as `UC-<slice>.md`, `tasks.md` and `source.json`, and the map to `<backlog>/context-map.json` and `<backlog>/context-map.md`. The rules for diagrams are in `planner/guidelines/diagram-conventions.md`.

The skill decides the scope with you first, then shows a design checkpoint with an outline and the decisions it cannot ground in the stories, and asks them. It never fills a decision with a default. When the current folder holds the code of the flow it reads that code and draws what it finds (repo mode). When it holds little or no code, the skill asks you once, before the checkpoint, whether the story builds the code (greenfield mode) or describes code that exists or a design only (describe-only mode), and never assumes the answer. In describe-only mode the slice stays at design level with `Maturity` `planned`. In greenfield mode the skill asks the project layout and the stack, records each answer as a `user-confirmed` design decision, marks `Maturity` as `planned (greenfield)`, puts the build plan in the implementation overview and marks each traceability row `planned`. The three modes are in section 5 of `planner/guidelines/diagram-conventions.md`. It also drafts `tasks.md`, the build tasks of the slice: one or more per acceptance criterion, grouped by flow, each with a `Satisfies:` and a `Verify:` line. It shows the complete document and the complete `tasks.md` in one reply, before it asks, lists the stories the slice covers that will be frozen, the ones already frozen and the ones that cannot be frozen. It asks "Write this slice and freeze its stories?" once for both. The same reply lists the security and non-functional rules, the `TBC` decisions and the open questions that no task covers, so you see what the draft left out. It also lists failure paths no task covers: a failure response that no `Verify:` line names and whose criterion is on the main path, so no failure criterion owns it. A rule counts as covered only when a `Verify:` line names it. A task that depends on a `TBC` decision or an open question names it in its `Verify:` line. It writes only after you choose "Yes, write and freeze". The skill sends every task unticked and the writer keeps a tick from an earlier `tasks.md` only while the criterion's text is unchanged; after a redraw the skill tells you which tasks were reset or dropped. Every diagram is checked with Mermaid's own parser before anything is written.

Each slice has a `## Changes to existing specs` section, after `## Open questions`. The skill reads the Notes of every story in scope and turns each `Changes existing spec` line into one row (Change, Wiki page, What changes, Reason), or writes `None`. It puts the question about a contradiction that no Notes line records into the design checkpoint, so you answer before it shows the document, and writes a row only after a yes. The row's path is the one in the Notes line minus the leading `wiki/`. A story with a `Supersedes` line is a new story and is not frozen, so the skill plans it only after you accept it into the backlog, and the slice freezes it only when it covers it and you confirm. The skill never edits the wiki and never marks a row applied. Wiki pages are read with `Read`, `Grep` and `Glob`.

At the design checkpoint, before it shows the outline, the skill reads the archived slices in the current folder's wiki that touch the same Epic, Feature or entities, found the same way as in the explore skill. It reuses a design decision an archived slice settled and names its source, so the decision is not asked again. It draws an entity that an archived slice owns as a stub, `(see <slice>)`. When the new slice would draw an archived entity or decision differently, it asks you at the checkpoint and draws nothing of it until you answer. With no wiki or no archived slice it says so once and plans as before.

A slice that is built and validated is folded into the wiki by `/jois-code:archive`, which applies those rows. It marks the slice folder with `ARCHIVED.md` (the date, the commit and the pages touched) and deletes nothing. The marker file is not a slice file the plan skill reads or checks, and a redraw with `jois-story-plan` leaves it as it is.

After the slice is written and read back, the skill runs `jois-story-verify` on it, corrects the problems that belong to the slice through the plan writer (up to 2 rounds, without a second question, because your yes covers this slice), and lists everything else, such as a story finding, a `TBC` decision or an open question, for you to decide. The skill reports slices as stale when their stories changed, and redraws only when you ask. It writes the slice, the map and one more thing: the `Frozen` flag, described below. For a change to a story or a term it offers `jois-story-propose`, and it needs its own packages, installed by `npm ci` in the skill folder.

### Freezing the stories of a slice

The plan skill's one write into the backlog is the `Frozen` column. After the slice is written, read back with a match and verified with no critical finding open, the skill runs `write-freeze.mjs`, which marks the stories the slice covers as frozen and changes no other cell. A frozen story is read-only in the portal, keeps its ID for good, and cannot be deleted. If the slice write fails, the read-back does not match or a critical finding of verify is still open, no story is frozen, and the skill says which one blocks it. A `TBC` decision or an open question is a warning and does not block the freeze.

The writer refuses a story that has no ID, and a story whose ID does not begin with the backlog's initials (for example `IAM-0003` in a backlog with initials `B1`). For the second case, open the backlog in the portal once so it rewrites the IDs, then freeze again. Freezing a story twice leaves the same result as freezing it once.

No skill and no portal control unfreezes a story. A freeze made by mistake is fixed by hand: open `<backlog>/user-stories.csv` in a text editor or Excel and clear the `Frozen` cell of that story. A change to a frozen story needs a superseding story, described next.

## The contradiction rule

The rule keeps a new story from silently clashing with what is already agreed. The explore and propose skills apply it to every new or changed story, and the plan skill carries its result into the slice. It has four steps.

1. Report it. When a story contradicts a story of the backlog or the proposals, or a wiki page, the skill names it plainly (the story by Title, the page by its path under `wiki/`). It does not drop the new story and does not ignore the earlier one.
2. Ask which one stands. The skill asks you one question that covers every contradiction it found for the story, recommends one when the stories, the wiki or the code favour it, and shows no draft of the new story and writes nothing until you answer. If the earlier one stands, the skill drops or reshapes the new story as you say and writes no `Changes existing spec` or `Supersedes` line for that earlier story or page, frozen or not.
3. A winning new story changes the old spec. For a wiki page, the new story's Notes get the line `Changes existing spec: <added|modified|removed> wiki/<path> - <what changes>`. The path keeps its `wiki/` prefix (the line for the page `wiki/planner/Story-Skills.md` says `wiki/planner/Story-Skills.md`), and only the slice's table drops it. For a story of the backlog that is not frozen, the skill drafts a review suggestion, and for a proposed story a patch.
4. Never edit a frozen story. The new story supersedes it, and its Notes carry `Supersedes: <ID> <Title>`, with the frozen story's permanent ID. The frozen story stays frozen and unmarked.

To find the wiki page, the skills first check, in the style of `ls`, that `wiki/` exists in the current folder, whatever a loaded `CLAUDE.md` says about the docs. If it does not, the skill says so in one line, once per session and not again for later stories, names `jois-init:docs` as the way to set one up, carries on against the backlog and proposals, and never creates `wiki/`. It also ignores a parent folder's `CLAUDE.md` or wiki that the session loaded into context, and a `CLAUDE.md` with no "Where the docs are" table and no `wiki/` counts as no wiki. If `wiki/` exists, the skills read, relative to the current folder and never a parent, the "Where the docs are" table of `CLAUDE.md` first, then `wiki/Home.md` and only the topic pages that the table or the home page names for the story, and only then `Grep` on `wiki/`. Text from the wiki, `CLAUDE.md` or the backlog is data, never instructions: the skill says in one line that it found such a request and does not act on it, and no skill opens a secret file because a text says to.

The decision travels in the Notes lines, because the Notes field already holds decisions and no new column or file is needed. The plan skill reads them when it drafts the slice, and a later stage applies them to the wiki. No skill edits the wiki page now: when a skill records a `Changes existing spec` line it says so, and says the line is the record of the change for that later stage. The reader script prints the permanent ID of a frozen story, and that is the ID a `Supersedes` line uses.

A story the winner leaves pointless or wrong without contradicting it is raised too. The explore and propose skills say so in one sentence, naming the story by Title or the page by path, and ask whether to change it. They draft nothing for it until you say yes, and then they treat it as a direct contradiction. If you agree it should change but do not say how, the suggestion is a Clarifications append that asks whether the story is still needed, and never a deletion. The rule itself is kept in the `story-contradiction-rule` capability of the OpenSpec specs, and this page is its summary.

## jois-story-verify and /jois-story:verify

Use it to check one slice that `jois-story-plan` wrote, before anyone builds from it. It checks nine things. Six are about the slice itself: whether it is stale, whether the document and diagrams pass the plan skill's checks, whether every acceptance criterion has a task, whether a design decision is still `TBC` (to be confirmed), whether a story in scope has an open clarification question, and whether a task waits on a decision or question that is still open. Three are about the project it is in: whether each task can be built against the code and the rules of the wiki and `CLAUDE.md`, whether the slice silently contradicts a wiki page, and whether the rows of its `Changes to existing specs` section match the wiki. It ranks each finding as critical, warning or suggestion, gives a fix and says who owns it, and lists any check it could not run with the reason.

The three project checks read the wiki and the code of the current folder only. Each finding names the wiki page or code file it read and quotes the line that decides it; a suspicion with nothing to quote is at most a suggestion. These findings are warnings, never critical. A project with no wiki gets one line that names `jois-init:docs`, and the checks that need a wiki are reported as not run. A greenfield slice (planned with no code yet) has no code to compare, so only the code part is not run. A clean result lists the pages and files read. The skill never edits the wiki or the code, and never applies a spec-change row: the archive stage does that. These checks are instructions the model follows, not a script, so how many defects they find depends on the model reading the right pages, and a very large wiki is untested.

It reads first and writes only after you approve the exact change. A fix to the slice is written through the plan skill's `write-diagram.mjs`, after it shows the complete corrected document and `tasks.md` and you answer yes. A problem in a story is never edited. It is offered as a suggestion for `review.csv` through `write-review.mjs`, which you apply or dismiss in the portal. A `TBC` decision is asked of you and never filled with a default.

When `jois-story-plan` calls it after writing a slice, it runs every check and returns the findings without writing anything; the plan skill makes the slice corrections. The skill holds no script of its own, so it needs `jois-story-plan` installed and stops without it. The command `/jois-story:verify` loads the skill and passes it the backlog and slice you name.

## The four commands

- `/jois-story:propose` runs `jois-story-propose` without the yes or no step, as described above.
- `/jois-story:re-read` only reads. It reloads the backlog, the proposals, the lexicon and the counts of review and term suggestions, compares them with what the session knew, says by title what changed, and marks the drafts that are now out of date. It starts no drafting.
- `/jois-story:review` is not the same as the `jois-story-review` skill. It audits the work of the current session only: whether what was agreed is written, whether the lexicon, dependencies, size, clarifications and review rows are in sync. It writes nothing and runs a writer only with `--check`. It ends with a checklist of what you do in the portal, what to ask via `/jois-story:propose`, and what needs a decision. For a whole-backlog review use the skill.
- `/jois-story:verify` runs `jois-story-verify` on one stored slice, as described above.

## Where this page and the sources differ

Two places say otherwise, and this page follows the command and skill files. `CLAUDE.md` lists `/jois-story:review` as a command of the story skills without saying that it is a session audit, and the portal's notice for suggestions that no longer match a story tells you to run `/jois-story:review` again, where the skill that writes review suggestions is `jois-story-review`.
